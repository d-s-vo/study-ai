# ADR-003: Слоистая архитектура (Domain / Application / Infrastructure) + инварианты слоёв

**Статус:** Принят (зафиксирован при инициализации `ai/`)
**Дата:** 2026-07-28

> Продуктовый decision-ADR. Фиксирует принятую при инициализации организацию кода Laravel-приложения cbook.

## Контекст

cbook переезжает на Laravel 11 (ADR-002). Дефолтный Laravel располагает к «толстым» контроллерам/моделям, где бизнес-логика размазана по HTTP-слою и Eloquent. Чтобы доменная логика рецептов (правила, инварианты, права по владельцу) не оказалась заперта в контроллерах и Filament-ресурсах и оставалась тестируемой в отрыве от фреймворка, принята явная слоистая организация с направленными зависимостями.

## Рассмотренные варианты

### Вариант А — Стандартный Laravel-layout (контроллеры + Eloquent-модели)
- **За:** меньше церемоний; привычно; быстрый старт.
- **Против:** бизнес-логика утекает в контроллеры/модели; трудно тестировать домен без БД/фреймворка; правила прав и инварианты рассеиваются.

### Вариант Б — Слоистая архитектура Domain / Application / Infrastructure (выбран)
- **За:** доменная логика изолирована и тестируема без Laravel; контроллеры/Filament тонкие; доступ к данным за репозиториями; явные границы упрощают ревью и приёмку по инвариантам.
- **Против:** больше слоёв и церемоний (DTO/VO, интерфейсы репозиториев); дисциплина направлений зависимостей держится ревью, а не компилятором.

## Решение

1. **Слои и направление зависимостей:** `Domain` ← `Application` ← `Infrastructure`/`Http`/`Filament`. **Domain не зависит от Infrastructure и от Laravel** (не импортирует Eloquent, фасады, HTTP).
2. **Domain:** сущности, value-objects, доменные правила рецептов; чистый PHP.
3. **Application:** сервисы/use-case, DTO, оркестрация доменной логики; сюда уходит бизнес-логика.
4. **Infrastructure:** Eloquent-модели и **реализации репозиториев** (интерфейсы объявлены в Domain/Application), внешние адаптеры (S3/MinIO). **Доступ к БД — через репозитории**, не Eloquent-запросами в контроллере/презентации.
5. **HTTP:** контроллеры **тонкие** (приняли запрос → делегировали в сервис → вернули Inertia-ответ); валидация — во **FormRequest/DTO**; авторизация — через **Policies/Gate** до бизнес-логики.
6. **Filament:** Resource'ы **без бизнес-логики**, делегируют в сервисы Application.
7. **Порядок создания сущности (инвариант):** миграция → Eloquent + репозиторий → Domain → сервис (Application) → контроллер/Inertia (+ FormRequest, Policy) → тесты (Pest, позитив + негатив прав).

## Последствия

- Инварианты слоёв прошиты в [`../guides/stack-specifics.md`](../guides/stack-specifics.md) §Инварианты и §Backend-специфика; против них проверяются тройная проверка spec (feature-workflow Шаг 5) и адверсариальная приёмка (live-acceptance).
- Роутер задач `../architecture.md` §0 для серверной фичи ведёт на эти инварианты.
- Источник энфорсмента направлений зависимостей — **ревью** (в т.ч. commit-review), а не автоматика; при желании позже можно добавить статические проверки границ (не входит в текущий профиль).
- Издержка: дополнительный код-церемония (DTO/VO, интерфейсы репозиториев) на каждую сущность.
