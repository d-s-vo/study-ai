# ADR-009: Детальный разбор «почему» каждого клиентского коммита (per-commit rationale)

**Статус:** Принят (системный ADR шаблона)

> Системный ADR методологии. Родился из режима секретности M6 (в клиентском коммите нельзя писать «почему»),
> но слой ценен и при **M6=OFF** как audit-trail. Правило: rationale-слой ОСТАЁТСЯ, если включён M2/оркестрация
> или явно нужен аудит. При развёртывании: подставь имена репозиториев/скриптов.

## Контекст

Правило «ноль следов системы» (ADR-001, `../architecture.md` §8) запрещает раскрывать рассуждения агента/ИИ в
клиентских коммитах: сообщение коммита обязано выглядеть как обычная человеческая работа. Значит канал «почему
сделано именно так» физически **недоступен** внутри клиентского репо — а этот канал владелец хочет иметь: по
каждому коммиту сторонний разработчик должен уметь восстановить обоснование, причём в двух уровнях — кратко для
опытного инженера и детально для новичка.

Существующие слои этого не покрывают: `ai/adr/` — уровень архитектуры (крупнее коммита),
`ai/devlog/features/FEAT-*/impl.md` — уровень фичи (описывает результат целиком, не разбирает отдельный коммит).
Нужен **новый покоммитный слой** объяснений, живущий вне клиентского репо и ссылающийся на существующие слои.

Дополнительная сложность — **устойчивость ключа**: агент коммитит на `feat/<slug>` локально
(`git push` запрещён), пользователь создаёт MR. Squash/rebase при мерже MR **меняет SHA** (squash уничтожает
исходные хеши в целевой ветке). Ключ «клиентский финальный хеш» ненадёжен по построению.

## Рассмотренные варианты

### Вариант (а) — Один markdown-файл на коммит в артефактном репо (выбран)
`ai/devlog/commits/<repo>/<hash>-<slug>.md`, шапка-frontmatter, тело — две секции в **одном** источнике:
«Кратко» (инженеру) + «Детально» (новичку).
- **За:** тот же паттерн, что уже используют фичи (markdown+frontmatter через `ai-commit.sh`); лёгкий `grep`;
  **лучшая устойчивость** — файл в НАШЕМ репо, ключ = as-authored hash + patch-id + FEAT, не зависит от того,
  что клиент сделал с историей MR; двухуровневость нативна (один источник → две аудитории, без рассинхрона).
- **Против:** связь с клиентским финальным хешем «мягкая» (дозапись после squash-мержа); дисциплина заполнения.

### Вариант (б) — git notes (`refs/notes/*`), ключ = клиентский SHA
- **Против (отклонён):** заметка привязана к SHA — rebase/squash MR её осиротит; слабый тулинг; «внешнее»
  хранение notes требует зеркала клиентского репо (запрещённо-неудобно).

### Вариант (в) — Папка на коммит, отдельные файлы по уровням
- **Против (отклонён):** кратно больше файлов/inode; главное — **два файла уровней разъезжаются** (анти-паттерн
  «раздельные версии для аудиторий»: обновили один — второй противоречит).

## Решение

Выбран **Вариант (а): один markdown-файл на коммит в артефактном репо.**

1. **Хранилище:** `ai/devlog/commits/<repo>/<as-authored-short-hash>-<slug>.md` (`<repo>` — по имени
   клиентского репо; `<slug>` — kebab-case смысл коммита).
2. **Ключ устойчивости (шапка):** as-authored **full hash**, `git patch-id --stable` (хеш от diff — переживает
   rebase), ветка, `FEAT-NNN`, дата. При squash/rebase MR файл **НЕ переименовывается**; в индекс добавляется
   колонка «итоговый хеш» best-effort. Три якоря (as-authored hash → patch-id → FEAT) дают найти разбор, даже
   если клиент переписал историю.
3. **Индекс:** `ai/devlog/commits/README.md` — конвенция + append-only реестр-таблица.
4. **Шаблон:** `ai/devlog/commits/_template.md` — frontmatter (repo/authored_hash/patch_id/branch/feat/date/
   final_hash?) + секции: **Кратко** (по каждому файлу 1–3 строки) · **Детально** (новичку, с расшифровкой
   терминов и приёмов по месту) · **Почему так, а не иначе** (отвергнутые альтернативы) · **Связи** (ссылками,
   не дублируя). Критерий готовности: по разбору можно ответить стороннему разработчику «почему сделано именно
   так», понятно даже новичку.
5. **Процесс:** разбор пишет **агент-исполнитель фичи** сразу после каждого коммита (или пачкой в конце фичи, до
   сводки), коммитит через `scripts/ai-commit.sh` (не `commit.sh` — это артефакт, не клиентский код).
   **Оркестратор** проверяет наличие разборов при приёмке (`adr-execution.md` B.2).

## Последствия

- **Дисциплина записи.** По каждому коммиту — отдельный файл-разбор; пропуск ловит оркестратор (B.2). Доп. шаг DoD.
- **Рост объёма.** Один markdown на коммит → сотни-тысячи файлов со временем. Стартовая раскладка — по репо; при
  разрастании (~500–1000 файлов) вводится один уровень шарда по префиксу short-hash — отдельным решением.
- **Squash/rebase.** Финальный клиентский хеш — «мягкая» связь; основной ключ устойчив к переписыванию истории.
- **Ноль следов сохраняется** (режим секретности M6 включён). Слой **ссылается** на ADR/impl/spec, не дублирует: три слоя
  (архитектура → фича → коммит) связаны ссылками.
