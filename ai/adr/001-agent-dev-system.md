# ADR-001: Агентская система разработки без следов (сепарация + git-броня + клетка возможностей)

**Статус:** Принят (системный ADR шаблона)

> Системный ADR методологии. Формулирует **двухконтурную модель** и **режим секретности** (модуль M6).
> При развёртывании: замени плейсхолдеры под проект. Если проект внутренний и ИИ-разработка официально
> принята (M6=OFF) — режим секретности сворачивается (см. «Альтернативы»), но **сепарация базы знаний и
> разделение привилегий остаются** (контуры совпадают, но каркас M1 — стержень, не опция).

## Контекст

Разработка ведётся AI-агентами через богатую внутреннюю систему контекста и процесса (архитектура, спеки,
ADR, живые документы инициатив, координация, ревью коммитов). Одновременно действует ограничение:
в режиме секретности (M6, включён в этом профиле) клиентские репозитории `cbook` не должны нести **ни одного следа** этой
системы — код, коммиты, ветки и MR обязаны выглядеть как обычная человеческая работа команды.

Конфликт: богатая внутренняя система разработки ↔ полное отсутствие её следов в поставляемом коде. Плюс код
клиента живёт в git-worktree, доставку делает пользователь, а не агент.

## Рассмотренные варианты

### Вариант А — Контекст внутри клиентского репо (`.ai-context/` в коде клиента)
- **За:** относительные ссылки на код работают из коробки; стандартный сценарий шаблонов баз знаний.
- **Против:** база знаний попадает в git клиента → прямая утечка следов; риск случайного коммита;
  несовместимо с требованием секретности.

### Вариант Б — Сепарация + git-броня + «клетка возможностей» (выбран)
- **За:** контекст в отдельном репозитории (`study-cbook-ai`, папка `ai/`) физически вне кода клиента;
  `.gitignore` артефактного репо исключает код клиента и секреты; коммиты в клиентские репы только через
  обёртку `scripts/commit.sh` (гейты + сканер следов); агентам запрещён `git push` (доставка — пользователь);
  рабочие пометки только `~wip~`, блокируются pre-commit хуком.
- **Против:** ссылки на код — от корня workspace (не относительные); нужна дисциплина «ревью чистоты»;
  часть механики (`scripts/`, `githooks/`) — вне зоны агента-инициализатора.

### Вариант В — Ручная зачистка перед доставкой
- **За:** простая ментальная модель.
- **Против:** ненадёжно (человеческая ошибка = утечка); не масштабируется на десятки фич и параллельных агентов.

## Решение

Выбран **Вариант Б: сепарация + git-броня + клетка возможностей.**

1. **Сепарация.** База знаний живёт в `ai/` (репозиторий `study-cbook-ai`), физически вне репозиториев кода;
   ссылки на код — пути **от корня workspace** (без `../` наружу из `ai/`). Это **двухконтурная модель**:
   клиентские проекты живут ВНУТРИ workspace, весь контекст работы сохраняется в родительском (артефактном)
   репозитории, а в клиентский репозиторий уходит только конкретный чистый коммит.
2. **Git-броня.** `.gitignore` артефактного репо исключает код клиента и секреты; коммиты в клиентские репы —
   только через `scripts/commit.sh` (гейты + сканер следов); `git push`/MR/merge на клиента — только
   пользователь (`scripts/deliver.sh`). Пуш артефактного репо — `scripts/ai-push.sh` (агенту разрешён).
3. **Клетка возможностей.** Временные пометки в коде — только `~wip~` (pre-commit хук блокирует их физически);
   финальный DoD — «ревью чистоты» свежим субагентом **без доступа к `ai/`**, читающим `git diff` как внешний
   ревьюер и ищущим следы системы / несоответствие стилю репо.

Инварианты решения: **сепарация артефактов**, **разделение привилегий** (агент пишет и коммитит локально;
push/доставка/fetch — привилегированный канал), **физический энфорсмент** (скрипты и хуки — источник истины;
документы описывают дисциплину, но не заменяют хук).

## Последствия

- Все ссылки на код в документах `ai/` — от корня workspace; никаких `../` наружу из `ai/`.
- В каждом гайде и брифе продублирован блок «Гигиена клиентского репозитория» (`../architecture.md` §8).
- Ветки — `feat/<slug>` без FEAT-номеров; маппинг FEAT ↔ ветка — в `../devlog/features/README.md`.
- Коммит-сообщения — в формате команды (`<type>: <описание> (conventional commits; type ∈ feat|fix|chore|refactor|docs|test|style|perf|build|ci)`); источник истины — `FORMAT_RE` в `commit.sh`.
- Часть механики (обёртка коммита, хуки, `task.sh`) — зона оркестратора/пользователя; агент-инициализатор её
  не трогает (guard-write блокирует запись в клетку).
- Rationale-слой «почему» физически не помещается в клиентский коммит → породил ADR-009 (per-commit rationale).

## Альтернативы на будущее (рычаг M6)

Если проект внутренний или клиент официально примет AI-ассистированную разработку — часть ограничений
(секретность имён веток/коммитов, «ревью чистоты», стоп-словарь следов) можно ослабить: §8 сворачивается в
короткую «гигиену коммитов», FEAT-номера могут жить в ветках. **Git-броня секретов/ПДн, сепарация базы знаний
и разделение привилегий остаются в любом случае.** Слой ADR-009 (rationale) при M6=OFF полезен как audit-trail.
