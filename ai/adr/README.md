# ADR — Architecture Decision Records

Записи об архитектурных решениях проекта. Каждое решение — отдельный `.md`-файл формата `NNN-slug.md`.

## Назначение

ADR отвечают на вопрос **«почему»** было принято решение (в отличие от `../architecture.md`, который
отвечает **«что»**). Обоснование живёт рядом с кодом-контекстом (в этой базе знаний), а не в голове автора.

## Формат

Карточка — по шаблону [`000-template.md`](000-template.md): заголовок, статус, контекст, рассмотренные
варианты, решение, последствия. Новый ADR — `NNN-slug.md`, следующий сквозной свободный номер по этому
каталогу. Нумерация **сквозная** и **не переиспользуется** (даже если ADR отменён — номер за ним остаётся).

## Два масштаба ADR (не путать)

- **decision-ADR одной фичи** — архитектурный выбор внутри обычной фичи. Авторится в
  [`../guides/feature-workflow.md`](../guides/feature-workflow.md) **§4.5**: одна карточка `NNN-slug.md`
  живёт здесь, в базе знаний (при включённом режиме секретности — **НЕ в клиентском коде**, см.
  `../architecture.md` §8), коммитится через `scripts/ai-commit.sh` (не `commit.sh`). Смена статуса
  `Принят → Реализован` — при закрытии фичи (feature-workflow Шаг 10).
- **ADR-инициатива** — крупный блок из десятков фич (оркестратор + субагенты). Канон исполнения —
  [`../guides/adr-execution.md`](../guides/adr-execution.md). **Одна карточка `NNN` = одно решение**, а не
  «по ADR на каждую фичу инициативы». Внутри карточки — раздел «План реализации» (таблица фаз/фич, keystone,
  журнал), скелет которого задан в `adr-execution.md` Часть A.

## Когда создавать ADR

- Выбор между несколькими технологиями/подходами с неочевидным компромиссом.
- Меняется уже принятое архитектурное решение → новый ADR со статусом «Заменяет ADR-XYZ» (старый не удаляем).
- Фиксируется неочевидный паттерн, который будут повторять (naming, auth-flow, границы модулей).
- **Brownfield:** легализация уже действующего решения «задним числом» при инициализации базы знаний
  (образец — [`_example-decision-adr.md`](_example-decision-adr.md); обоснования НЕ выдумывать — фиксировать
  реально действовавшие силы).

## Когда ADR не нужен

- Мелкие выборы внутри одного модуля; локальные оптимизации.
- Решения, полностью описанные шаблоном (структура файлов, naming convention — это ОДИН ADR, не по одному
  на сущность).

## Системные ADR методологии (входят в шаблон)

Ниже — процессные ADR самой системы агентской разработки. **Номера сохранены как в исходной системе**
(001/004/009/010), потому что гайды ссылаются на них по номеру — перенумерация ломает ссылки. Системные
ADR отключённых в этом профиле модулей — 005 (M5, контейнерная изоляция) и 008 (M3, quality-ratchet) —
удалены вместе с модулями; их номера **не переиспользуются**. Продуктовые ADR проекта заняли 002/003/006
(см. «Реестр проектных ADR» ниже); 007 и далее — свободны.
