# Dev Log & Feature Planning

> ⚠️ **Перед началом работы по любой фиче** — прочитай гайд:
> **`ai/guides/feature-workflow.md`** — обязательный алгоритм: spec → тройная проверка → тесты → реализация → impl.md.

Система планирования и документирования разработки текущего проекта.

---

## Структура

```
devlog/
├── README.md              # Этот файл
├── YYYY-MM-DD.md          # Ежедневные записи + канал ## Quickfixes
└── features/              # Фичи (полный цикл: spec → impl → retro)
    └── FEAT-NNN-slug/
        ├── spec.md        # Техническое задание (до реализации)
        ├── impl.md        # Как реализовали (после реализации)
        └── retro.md       # Ретроспектива (опционально, для крупных)
```

---

## Фичи (`features/FEAT-NNN-slug/`)

Полный цикл разработки фичи:

### 1. `spec.md` — Техническое задание (ДО реализации)
- Цель (что делаем и зачем)
- Контекст
- Acceptance Criteria (наблюдаемые результаты)
- Технический дизайн
- Тесты (новые / изменяемые / удаляемые)
- Безопасность
- Зависимые файлы
- Что НЕ входит в фичу
- Оценка сложности

Подробный шаблон — в [`../guides/feature-workflow.md`](../guides/feature-workflow.md) шаг 4.

### 2. `impl.md` — Реализация (ПОСЛЕ работы)
- Что сделано (файлы → изменения)
- Отклонения от spec (если есть)
- Ключевые решения по ходу
- Как тестировали (команды, результаты)
- Итог

### 3. `retro.md` — Ретроспектива (опционально)
- Что подошло, что нет
- Уроки для будущих фич
- Следующие шаги / технический долг

### YAML frontmatter в `impl.md` (опционально, рекомендуется)

Для grep-индексируемости gotchas по классу багов — каждое `impl.md` может начинаться с YAML frontmatter:

```markdown
---
feat: FEAT-NNN
tags: [<category>, ...]
class: '<1 предложение — что чинили/добавляли>'
prevention: '<lint rule / test pattern / class-guard>'  # если добавили структурный guard
---

# FEAT-NNN: Название — Implementation

**Статус:** DONE
...
```

**Поля:**

| Поле | Обязательность | Когда |
|---|---|---|
| `feat` | Рекомендуется | ID фичи (для grep-парсинга) |
| `tags` | Рекомендуется | Массив kebab-case категорий баг-класса (см. каталог ниже) |
| `class` | Опционально | Одно предложение «что чинили/добавляли» |
| `prevention` | Опционально | Какой guard/lint/test добавили для предотвращения повтора |

**Каталог тегов (initial, расширяемый под проект)** — категории баг-класса, не компонента. Адаптируйте под свой стек:

| Категория | Когда ставить |
|---|---|
| `regression-test-missing` | Баг без регрессионного теста |
| `scope-creep` | Фича разрослась за пределы spec |
| `type-narrowing` | Типовый narrowing не сработал, fallthrough в wrong branch |
| `perf-hot-path` | Проблема производительности в горячем пути |
| `security-leak` | Утечка секрета / PII / доступа |
| `auth-bypass` | Authz-политика пропущена / некорректна |
| `migration-backward-compat` | Миграция схемы данных ломает обратную совместимость |
| `concurrency-race` | Гонка между concurrent операциями |
| `validation-missing` | Входные данные не валидируются до бизнес-логики |
| `error-swallowing` | Ошибка проглатывается без логирования |
| `type-coverage-regression` | Новый код ослабил типовую строгость / регресс сверх baseline (ADR-008) |
| `lint-threshold-violation` | Превышен порог сложности/размера или ослаблен baseline линта (ADR-008) |
| `docs-only` | Изменение только в гайдах/spec (не код) |

**Grep-сценарии:**

```bash
# Все фичи с конкретным классом багов
grep -l 'tags: .*security-leak' ai/devlog/features/*/impl.md

# Все фичи, добавившие lint-guard
grep -l 'prevention: .*lint:' ai/devlog/features/*/impl.md

# Топ тегов (для анализа паттернов)
for f in ai/devlog/features/*/impl.md; do
  head -10 "$f" | grep -E '^tags:'
done | sort | uniq -c | sort -rn
```

**Расширение каталога:** новая категория → добавить строку в таблицу выше; единый источник = этот файл (избегайте рассинхрона между `devlog/README.md` и `architecture.md`).

## Ежедневные записи (`YYYY-MM-DD.md`)

Краткие записи о том, что произошло за день + канал для **trivial-fix** (см. `feature-workflow.md` Шаг 0 §Trivial-fix shortcut):

```
devlog/
├── README.md              # Этот файл
├── YYYY-MM-DD.md          # Ежедневные записи + раздел ## Quickfixes
└── features/              # Фичи (полный цикл)
    └── FEAT-NNN-slug/
```

**Формат записи:**

```markdown
# YYYY-MM-DD

## Решения
- Выбрали X для Y, потому что Z (ссылка на ADR-NNN)

## Изменения
- Деплой на dev завершён

## Quickfixes

- quickfix-typo-readme: опечатка в README (1 файл, 8 LOC)
- fix-foo-import: замена deprecated API call (1 файл, 12 LOC)
```

**Когда писать:** в конце дня, если были nontrivial-изменения, **обязательно** — если был хотя бы один quickfix или merge. Файл создаётся один раз и дописывается в течение дня.

## Нумерация фич

`FEAT-NNN` — порядковый номер. Slug — краткое kebab-case описание.

Если проект ведёт несколько клиентских репозиториев (`cbook`) — нумерация **сквозная**
на все них: один номер FEAT привязан к одной работе, независимо от того, в каком репо она отдана.

```bash
# Определить следующий номер:
ls ai/devlog/features/ 2>/dev/null | sort | tail -5
```

Занятые номера и маппинг FEAT-NNN ↔ ветка (если включён режим секретности, модуль M6) — в
[`features/README.md`](features/README.md).

---

## Правила

1. **Один slug — одна ответственность.** Не смешивай разные уровни.
2. **Spec пишется ДО реализации.** Не ретроспективно.
3. **impl.md создаётся только по завершении.** Не как пустышка.
4. **После фичи — обязательно обновить `../memory.md`** (см. feature-workflow.md шаг 10).
5. **Имя файла внутри FEAT — в lowercase** (`spec.md`, `impl.md`, `retro.md`).
