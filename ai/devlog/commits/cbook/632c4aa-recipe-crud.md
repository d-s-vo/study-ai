# cbook@632c4aa — мутации рецептов с проверкой владельца

> Коммит-сообщение (как в клиентском репо): `feat: мутации рецептов с проверкой владельца`

## Кратко (для инженера)

- `app/Policies/RecipePolicy.php` — центральная точка authz домена: view/viewAny/create → true (общий каталог, гейт — маршрутная middleware), update/delete → `$user->id === $recipe->user_id`. Autodiscovery Laravel 12, регистрация не нужна.
- `app/Tasks/{Create,Update,Delete}RecipeTask.php` — по бизнес-операции на класс (канон: `final`, `private readonly` DI репозитория, вход через `run()`); Create/Update отделяют `ingredients` от атрибутов рецепта и делегируют в `RecipeRepository`. Моделей и Eloquent в Tasks нет.
- `app/Http/Requests/StoreRecipeRequest.php` — вся серверная валидация мутаций: скаляры, `Rule::enum(Difficulty::class)`, вложенные `steps.*`/`ingredients.*.*`. `user_id` в правилах отсутствует намеренно (владелец — из auth). `UpdateRecipeRequest` наследует Store (полная замена рецепта).
- `app/Http/Controllers/RecipeController.php` — тонкий: store берёт владельца из `$request->user()->id`; update/destroy — `findModel($id)` → `abort_if(null, 404)` → `Gate::authorize(...)` → Task → redirect `dashboard` (redirect-таргет временный, до появления страниц рецептов). Имя класса модели в исходнике не упоминается — арх-барьер не задет.
- `routes/web.php` — `recipes.store/update/destroy` с `whereNumber('recipe')` в группе `['auth','verified']`; profile-группа переведена с `auth` на `['auth','verified']` (долг ревью включённой email-верификации).
- `tests/Feature/ArchitectureTest.php` — allow-list `App\Models` расширен на `App\Policies` (Policy получает уже загруженную модель, запросов не делает; правило по фасаду `DB` неизменно).
- `tests/Feature/Recipe/RecipeCrudTest.php` — позитивы CRUD + обязательные негативы: чужой PUT/DELETE → 403 (ядро фичи, анти-IDOR), `user_id` в payload игнорируется, guest → login, unverified → verification.notice, 404 по несуществующему id, датасет валидационных отказов.
- `tests/Feature/ProfileTest.php` — негатив: неверифицированный на `/profile` → redirect `verification.notice`.

## Детально (для новичка)

### Зачем это всё: IDOR и слоистая архитектура

IDOR (Insecure Direct Object Reference) — класс уязвимости, когда пользователь подставляет чужой id в URL (`PUT /recipes/7`) и сервер послушно меняет чужие данные, потому что проверил только «залогинен ли», а не «его ли это объект». Защита в этом коммите структурная: каждый мутационный маршрут до бизнес-логики проходит через Policy, которая сравнивает владельца рецепта с текущим пользователем. Не «владелец» → 403 Forbidden, и это закреплено обязательными негативными тестами.

Поток запроса в принятой архитектуре: FormRequest (валидация) → Controller (тонкая склейка) → Task (бизнес-операция) → Repository (единственное место запросов к БД). Авторизация — между валидацией и Task.

### `app/Policies/RecipePolicy.php`

Policy — стандартный механизм Laravel: класс, отвечающий на вопрос «может ли пользователь X сделать действие Y с объектом Z». Laravel 12 находит её автоматически по конвенции имён (`App\Models\Recipe` → `App\Policies\RecipePolicy`) — код регистрации не нужен. `view`/`viewAny` возвращают `true` не потому, что «просмотр без ограничений вообще», а потому, что реальный гейт просмотра — middleware `auth`+`verified` на маршрутах: каталог общий для всех вошедших. Методы оставлены явно, чтобы контракт был виден и его легко сузить.

### `app/Tasks/*RecipeTask.php`

Task — «одна бизнес-операция = один класс»: контроллер не знает, как именно создаётся рецепт с ингредиентами, он лишь вызывает `run()`. Payload приходит одним массивом из FormRequest; Task отделяет `ingredients` (композиционная часть агрегата) от атрибутов рецепта и передаёт репозиторию, который делает всё в транзакции. Заметьте: Tasks не упоминают ни одну Eloquent-модель — это принудительно проверяется арх-тестом.

### `app/Http/Requests/StoreRecipeRequest.php` и `UpdateRecipeRequest.php`

FormRequest — класс запроса, в котором живёт вся валидация: контроллер получает уже проверенные данные через `validated()`. Ключевые приёмы: `Rule::enum(Difficulty::class)` валидирует значение по enum (нельзя прислать `difficulty=extreme`); правила с точечной нотацией (`ingredients.*.name`) проверяют каждый элемент вложенного массива. Важное отсутствие: `user_id` в правилах нет — даже если клиент пришлёт его в payload, `validated()` его отбросит, а владельцем станет автор запроса. Это второй эшелон против подмены владельца (первый — `user_id` вне `$fillable` модели). `authorize()` в Request возвращает `true`: проверка прав на объект здесь невозможна по смыслу (Request не знает о рецепте), она живёт в Policy.

`UpdateRecipeRequest extends StoreRecipeRequest` — обновление задумано как полная замена рецепта, правила идентичны; наследование избавляет от дублирования и расхождений в будущем.

### `app/Http/Controllers/RecipeController.php`

Тонкий контроллер с приёмом «авторизация без упоминания модели»: в проекте действует арх-запрет на использование `App\Models\*` вне репозиториев, поэтому контроллер не может тип-хинтить `Recipe`. Вместо route-model-binding маршрут отдаёт голый `int $recipe`; контроллер просит модель у репозитория (`findModel`), проверяет «не найдено» через `abort_if(..., 404)` и передаёт объект в `Gate::authorize('update', $found)` — Laravel сам сматчит его с `RecipePolicy::update`. Имя класса модели в файле не встречается ни разу, поэтому барьер спокоен, а статанализ (Larastan) всё равно знает реальный тип переменной и держит уровень 10 без подавлений.

Та же логика — почему в `store` берётся `$request->user()->id`, а не каст `getAuthIdentifier()`: Larastan выводит модель пользователя из конфига auth, свойство `id` уже `int`, и каста (которые в проекте запрещены как подавление) не требуется.

После успеха все три метода редиректят на `dashboard` — страниц рецептов ещё нет; когда появятся, поменяются только redirect-таргеты и ассерты.

### `routes/web.php`

Мутационные маршруты собраны в группу `middleware(['auth','verified'])` — гость получает redirect на login, вошедший без подтверждённой почты — на страницу верификации. `whereNumber('recipe')` — ограничение параметра на уровне роутера: `PUT /recipes/abc` даст 404, не дойдя до контроллера. Сюда же переведена profile-группа (`auth` → `auth`+`verified`) — закрытие давнего замечания: раз в проекте включена email-верификация, личный кабинет не должен быть доступен до подтверждения почты.

### Тесты

`RecipeCrudTest` строится вокруг негативов, потому что ядро фичи — права: два пользователя, рецепт одного, попытки другого изменить/удалить → строго 403 и неизменённые данные в БД. Отдельный кейс — подмена владельца через payload (`user_id` чужого в POST): рецепт всё равно принадлежит автору запроса. Валидационные отказы оформлены датасетом Pest (`with([...])`) — один тест, четыре сценария плохого ввода, каждый проверяет и ошибку в сессии, и отсутствие записи. В `ArchitectureTest` allow-list расширен на `App\Policies` с комментарием-обоснованием: Policy — санкционированная точка касания модели вне репозитория (читает атрибуты уже загруженного объекта, запросов не делает).
