# cbook@b0a56ff — доступ администратора к панели и супер-доступ к рецептам

> Коммит-сообщение (как в клиентском репо): `feat: доступ администратора к панели и супер-доступ к рецептам`

## Кратко (для инженера)

- `database/migrations/2026_08_03_000001_add_is_admin_to_users_table.php` — `users.is_admin` (`boolean`, `default(false)`, `after('email_verified_at')`).
- `app/Models/User.php` — `implements FilamentUser`; `canAccessPanel(Panel $panel): bool` → `$this->is_admin && $this->hasVerifiedEmail()`; `is_admin` добавлен в `casts()` как `boolean`; **не добавлен** в `$fillable` (осознанно).
- `app/Policies/RecipePolicy.php` — `before(User $user): ?bool` → `$user->is_admin ? true : null`. Возврат `true` для админа даёт супер-доступ ко всем методам политики без исключения; `null` для обычного пользователя не меняет существующее поведение (owner-scoping из FEAT-010 остаётся в силе).
- `database/factories/UserFactory.php` — `+admin()` state (`is_admin => true`) для тестов.
- `app/Console/Commands/GrantAdminCommand.php` — `app:grant-admin {email}`; ищет пользователя по почте через `UserRepository`, делегирует выдачу прав, возвращает `FAILURE`/`SUCCESS` с сообщением. Не содержит `App\Models\Recipe`/Eloquent — только вызов репозитория.
- `app/Data/Repositories/UserRepository.php` — `+grantAdminByEmail(string $email): bool` (`User::query()->where('email', ...)->first()`, `forceFill(['is_admin' => true])->save()`, `false` если не найден); `+selectOptions(): array` (`id => name`, отсортировано по имени — источник опций для Select "Author" в будущем `RecipeForm`).

## Детально (для новичка)

### Зачем это всё: least privilege плюс осознанный супер-доступ

Этот коммит закладывает две разные вещи, которые легко перепутать: (1) кто вообще может *войти* в `/admin`, и (2) что может делать администратор *внутри* домена (рецепты). Первое — новая поверхность доступа, второе — уточнение уже существующей authz-модели (`RecipePolicy` из FEAT-010). ADR-011 требует, чтобы оба решения были явными и не ослабляли существующие защиты по умолчанию.

### Флаг `is_admin`: вне `$fillable` — это не забывчивость

Миграция добавляет `is_admin boolean default false` — по умолчанию никто не админ, это и есть least privilege. Модель кастует поле в `casts()` (чтобы `$user->is_admin` возвращало настоящий `bool`, а не `0`/`1` из БД), но **намеренно не добавляет `is_admin` в `$fillable`**. `$fillable` — это allow-list полей, которые можно массово присвоить через `User::create($data)`/`$user->fill($data)` из пользовательского ввода (например, формы профиля). Если бы `is_admin` был в `$fillable`, любой эндпоинт, принимающий произвольный массив атрибутов пользователя, теоретически позволил бы подсунуть `is_admin: true` и самому себе выдать права — классическая эскалация привилегий через mass assignment. Поэтому единственный путь установить флаг — `forceFill()` (обходит защиту `$fillable` осознанно, вызывается только из `UserRepository::grantAdminByEmail`, которую, в свою очередь, вызывает только консольная команда, а не HTTP-контроллер).

### `FilamentUser::canAccessPanel()`

Filament перед тем, как пустить пользователя в панель, спрашивает у модели: "можешь ли ты сюда"? Контракт `FilamentUser` требует ровно один метод — `canAccessPanel(Panel $panel): bool`. Реализация здесь — конъюнкция двух условий: `is_admin` (флаг роли) и `hasVerifiedEmail()` (тот же метод `MustVerifyEmail`, что и для верификации на публичном сайте). Второе условие важно само по себе: администратор с неподтверждённой почтой в панель не попадёт, даже если флаг уже стоит — это закрывает окно между "создали учётку админа" и "админ подтвердил почту".

### `RecipePolicy::before()` — как работает супер-доступ, не трогая остальные методы

Laravel Policy поддерживает специальный метод `before()`: если он определён и возвращает не-`null`, это значение становится финальным вердиктом для *любого* метода политики (`view`, `update`, `delete`, ...), остальные методы даже не вызываются. Возврат `null` — сигнал "у меня нет мнения, спроси у обычного метода дальше" (`view`/`update`/`delete` из FEAT-010 отрабатывают как прежде). Поэтому для админа (`is_admin === true`) `before()` возвращает `true` — супер-доступ ко всем действиям над любым рецептом; для обычного пользователя — `null`, и владелец-скоуп (сравнение `$user->id === $recipe->user_id`) продолжает работать без изменений. Это ключевое свойство: изменение сделано в одну строку и не требует трогать существующие негативные IDOR-тесты FEAT-010 — они остаются зелёными, потому что путь для не-админа не изменился.

### `GrantAdminCommand` и `UserRepository`

Выдача прав — не HTTP-эндпоинт (никакой формы "сделать себя админом" в приложении нет), а консольная команда, запускаемая оператором вручную: `php artisan app:grant-admin user@example.com`. Команда сама не трогает Eloquent — принимает почту, зовёт `UserRepository::grantAdminByEmail()`, которая ищет пользователя и делает `forceFill`. Это соответствует слоистой архитектуре проекта: обращения к моделям — только в репозиториях, команда — просто тонкий вызывающий код (как контроллер).

`selectOptions()` в том же репозитории — забегающая вперёд подготовка для следующего коммита (`RecipeResource`): выпадающий список "автор рецепта" в форме админки должен показывать `id => name` всех пользователей, и эта выборка тоже идёт через репозиторий, а не напрямую из `Filament\Forms\Components\Select` в обход барьера.

## Почему так, а не иначе

- **`forceFill` вместо добавления `is_admin` в `$fillable`** — отклонено расширение `$fillable`: удобнее один раз, но открывает mass-assignment эскалацию прав через любую будущую форму, принимающую атрибуты `User`. `forceFill` в единственном контролируемом месте безопаснее.
- **`before()` в Policy вместо проверки `is_admin` в каждом методе (`view`/`update`/`delete`) по отдельности** — `before()` короче, не дублирует условие в трёх местах и семантически точно передаёт "супер-доступ поверх обычной логики", а не "ещё один частный случай владения".
