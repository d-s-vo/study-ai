# Гайд: Координация параллельной работы нескольких агентов

> Читай **до старта работы**, если в workspace одновременно трудится больше одного агента
> (или может появиться второй). Слой координации живёт в `ai/coord/`, инструменты — `scripts/coord.sh`,
> `scripts/gate.sh`, `scripts/ai-commit.sh`.

## Зачем этот слой

Несколько агентов работают в одном workspace под **разными аккаунтами** агента (разные
конфиг-директории). Общего у них — только **файловая система**: ни общей памяти, ни общего процесса,
ни внутренних механизмов агентского рантайма. Поэтому вся синхронизация — через файлы в `ai/coord/`
и mkdir-мьютексы. Слой решает три проблемы параллельности:

1. **Кто над чем работает** — брони фич (`bookings/`), видимые всем.
2. **Изоляция окружений** — изолируешь вручную (эфемерная тестовая БД Sail и/или `.env.testing` с
   `RefreshDatabase`, свой backend/frontend на отдельном порту); нет отдельного скрипта изоляции —
   главное правило: невлитый код никогда не гоняется по общей dev-БД.
3. **Сериализация общих ресурсов** — тяжёлые/эксклюзивные операции под гейт-локом.

Общий `.git` (bare `.repos/<repo>.git`) — общий на все worktree, поэтому `git stash` в worktree
**запрещён** (см. [`./feature-workflow.md`](./feature-workflow.md) §3.5): вытащит чужой WIP.

## Жизненный цикл задачи (по шагам)

```bash
# 0. Старт сессии — хук coord-session-start.sh уже показал тебе живых агентов и брони.
#    Первым делом подтяни входящие изменения:
./scripts/sync.sh

# 1. Забронируй фичу (под локом booking: атомарно выделяются FEAT/индекс/порты):
./scripts/coord.sh book <slug>                 # обычная фича
./scripts/coord.sh book <slug> --repo <repo>   # фича в другом репо реестра repos.conf
./scripts/coord.sh book <slug> --adr           # если фиче нужен ADR — выделит и ADR-номер
# Мультирепная фича (один FEAT на несколько репо): бронь и worktree — ПО ОДНОЙ НА РЕПО,
# рецепт — feature-workflow.md §3.5 «Фича, затрагивающая несколько репозиториев».

# 2. Создай ветку + worktree:
./scripts/task.sh new <slug>                   # ветка feat/<slug>, папка tasks/<slug>

# 3. Изолируй окружение вручную (эфемерная тестовая БД Sail и/или .env.testing/RefreshDatabase,
#    свой backend/frontend на отдельном порту) — ПОСЛЕ task.sh new:
#    никогда не гоняй невлитый код по общей dev-БД.

# 4. Работай в tasks/<slug>. Меняй статус по мере продвижения:
./scripts/coord.sh update <slug> --status spec
./scripts/coord.sh update <slug> --status impl
./scripts/coord.sh update <slug> --status verify

# 5. Тяжёлые/эксклюзивные операции — через гейт (сериализация между агентами):
./scripts/gate.sh <ресурс> -- <команда>        # имена ресурсов — architecture.md §0 / stack-specifics.md

# 6. Вехи в общих артефактах study-cbook-ai — только через ai-commit.sh (лок shared-docs):
./scripts/ai-commit.sh "DOCS / ... / веха" ai/devlog/features/FEAT-NNN-<slug>/

# 7. Доставка в клиентскую репу — ТОЛЬКО пользователь (scripts/deliver.sh). Агент не пушит.

# 8. После merge — уборка (оркестратор/пользователь):
./scripts/sync.sh --cleanup                    # уберёт merged-worktree и перенесёт бронь в archive/
#    снеси свою эфемерную тестовую БД/окружение вручную (sync сам НЕ дропает)
```

> **Порядок — изоляция окружения ПОСЛЕ task.sh new** — обязателен: `git worktree add` отказывается
> писать в непустой каталог, поэтому окружение (`.env`) настраивается только в уже созданном worktree.

## Что выделяет бронь

По индексу `N` (минимальный свободный `1..9`) бронь фиксирует **непересекающиеся** ресурсы: порты
сервисов, redis-db. **Источник истины формул — `scripts/coord.sh` (`cmd_book`)**;
конкретные базы портов и правила пропуска зарезервированных db — параметр развёртывания
`база + index*10; конкретные базы портов — в scripts/coord.sh (cmd_book)`
(в шаблоне не дублируются, чтобы не разошлись со скриптом). БД задачи скриптом не выделяется —
изолируй вручную (эфемерная БД Sail / `.env.testing` с `RefreshDatabase`).

| Ресурс | Как выделяется | Источник истины |
|--------|----------------|-----------------|
| порты сервисов (backend/frontend/…) | сдвиг по `N` от базы (`база + index*10; конкретные базы портов — в scripts/coord.sh (cmd_book)`) | `scripts/coord.sh` |
| redis db | по `N`, с пропуском зарезервированных под общий брокер | `scripts/coord.sh` |
| БД задачи | изолируй вручную: эфемерная тестовая БД в Sail / `.env.testing` (`RefreshDatabase`) | ты сам, ручной шаг |

**Неизолируемый общий ресурс**: общий Redis (кэш и очереди Laravel) и общий Postgres-сервис Sail
(`pgsql`) — один брокер/одна БД на все параллельные задачи, M4 (env-isolation) выключен, поэтому
автоматически не разводятся. Тяжёлые прогоны, которые бьют по этим общим сервисам (полный тест-сьют,
воркер очереди, миграции на общей БД), запускаются **только под гейт-локом**
(`./scripts/gate.sh <ресурс> -- <cmd>`) — иначе, например, воркеры очереди разных задач разберут
чужие джобы из общей очереди Redis, либо параллельные миграции столкнутся на одной БД. Эфемерную
БД/схему под задачу (Sail + `.env.testing`, `RefreshDatabase`) разводи вручную — авто-изоляции нет.
Принцип общий: **неизолируемый общий ресурс → сериализация через `gate.sh`**.

## Статусы брони ↔ глифы фичи

Статус брони (`coord.sh update <slug> --status …`) и глиф фичи в `devlog/features/README.md` —
это разные измерения одной работы. Короткий маппинг:

| Статус брони | Глиф фичи | Смысл |
|--------------|-----------|-------|
| `planned`    | ⬜        | забронировано, работа ещё не началась |
| `spec`       | 🚧 (spec) | пишется спека (specs-first), кода ещё нет |
| `impl`       | 🚧        | реализация в работе |
| `verify`     | 🚧        | реализовано, идёт верификация/гейты |
| `delivered`  | 🚧 передано | локальный коммит готов и отдан на интеграцию (ждём merge) |
| `merged`     | ✅        | смержено на клиента — бронь уходит в `archive/` |

Глиф-модель фич (⬜/🚧/✅ и их значения на уровне ADR-инициативы) — в
[`./adr-execution.md`](./adr-execution.md): статус брони отражает **оперативный ход**, глиф в README —
**итоговое состояние** фичи в живом документе инициативы.

## Правила

- **Пиши только в свою FEAT-папку** (`ai/devlog/features/FEAT-NNN-<slug>/`) и в свой worktree
  `tasks/<slug>/`. Чужие — не трогай.
- **Общие md whitelist** в `study-cbook-ai` (`architecture.md`, `memory.md`, `devlog/README.md`,
  `devlog/features/README.md`, дневные `devlog/YYYY-MM-DD.md`, `guides/*`) — правь **только через
  `./scripts/edit-shared.sh "<msg>" <путь>… -- <команда-правки>`**: он берёт edit-cycle-lock
  `edit-shared` на ВЕСЬ цикл read-modify-write (не только на коммит), потом коммитит через
  `ai-commit.sh`. Команда-правки обязана завершиться синхронно (**не бэкграундить** `… &` — лок
  снимется раньше конца правки). Так два инстанса, правящие один файл, сериализуются без потерь.
  (Конкретный whitelist — под структуру `ai/` проекта; источник истины — `scripts/edit-shared.sh`.)
- **`ai/adr/*` и изолированные FEAT-папки** — НЕ через `edit-shared.sh`: коммить
  `./scripts/ai-commit.sh` (commit-lock `shared-docs` на git-индекс, любой путь `study-cbook-ai`). Живой
  ADR под исполнением координируется дисциплиной [`./adr-execution.md`](./adr-execution.md) B.4
  (журнал §N.6 — своя строка append; keystone §N.5 — серийно через оркестратора); обёртка
  `edit-shared` ему не нужна и не разрешена.
- **Порядок взятия локов** (против дедлока): `booking` → `edit-shared` → `shared-docs`, всегда;
  `ai-push` не вкладывается. **Push `study-cbook-ai`** (`ai-push.sh`) сериализован локом `ai-push`
  (`pull --rebase`-retry в критической секции); занятая очередь дольше таймаута = **REQUEUE**
  (мягкий повтор, exit 75), не ошибка.
- **Неизолируемые общие ресурсы** (см. выше) — только под `gate.sh`.
- **Лимит 3–5 агентов** одновременно (индексов `1..9`, но борьба за общий Postgres/Redis/сеть/RAM
  растёт нелинейно). Больше — координируй через оркестратора.
- **`git stash` в worktree запрещён** — общий `.git` (см. [`./feature-workflow.md`](./feature-workflow.md) §3.5).

## Присутствие и heartbeat

- Хук `coord-session-start` регистрирует тебя в `ai/coord/agents/<session_id>.json` и показывает сводку.
- Хук `coord-heartbeat` (PostToolUse) обновляет твой heartbeat (троттлинг: не чаще раза в ~60с).
- Хук `coord-session-end` убирает твой файл присутствия.
- `coord_reap` (внутри `sync.sh`/`status.sh`/`coord.sh`) чистит записи с протухшим heartbeat;
  мёртвый pid лишь **ускоряет** реап (пороги — в `scripts/lib/coord.sh`).

## Протухшие локи и брошенные брони

- **Протухший лок**: `coord_lock` **перехватывает** лок автоматически с предупреждением —
  руками ничего чистить не надо. Живость владельца определяется **heartbeat'ом его session**
  (mtime файла присутствия) и **owner-mtime** самого лока, а НЕ `kill -0` по pid (см. K-live
  ниже). Если совсем застрял — каталог `ai/coord/locks/<имя>.lock` можно удалить вручную
  (убедись, что владелец мёртв: нет живого heartbeat и owner-mtime старый).
- **Правило toucher'а:** держатель **длинной** секции (гейт, push, edit-cycle) ОБЯЗАН фоново
  освежать owner-mtime — запускать `coord_lock_toucher <имя> &` сразу после `coord_lock` и
  снимать его в `trap` (образец — `scripts/gate.sh`). Без toucher'а лок протухнет по owner-mtime
  через `COORD_LOCK_MTIME_STALE` (значение — в `scripts/lib/coord.sh`) даже при живой сессии (напр.
  держатель убит `SIGKILL`). Короткие локи (секунды) toucher не нужен — owner-mtime свежий с момента
  захвата.
- **Брошенная бронь** (агент ушёл, статус не `merged`): её присутствие вычистит `coord_reap`, но
  сама бронь останется. Сними её осознанно: `./scripts/coord.sh unbook <slug> --force`
  (для не-`merged` нужен `--force` — это подтверждение, что работа брошена). Не забудь снести
  свою эфемерную тестовую БД/окружение вручную.

## Диагностика

```bash
./scripts/coord.sh agents      # кто онлайн
./scripts/coord.sh board       # все брони + счётчик архива
./scripts/status.sh            # полная панель (агенты + брони + репы + task-ветки)
./scripts/coord.sh reap        # руками вычистить протухшие сессии
```
