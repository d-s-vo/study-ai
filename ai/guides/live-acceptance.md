# Live-приёмка — проверка «система реально работает» (часть DoD)

> **Аудитория:** AI-ассистент и разработчик проекта.
> **Когда сюда:** фича «готова» (тесты зелёные) — но её ещё **не запускали живьём**. Живая приёмка — **обязательная часть Definition of Done**, не опция.
> **Когда НЕ сюда:** ищешь причину уже случившегося бага → [`./debugging.md`](./debugging.md). Пишешь фичу → [`./feature-workflow.md`](./feature-workflow.md).

> ⛔ **Гигиена клиентского репозитория** (см. `../architecture.md` §8) действует и в приёмке: в stdout/логах прогона нет секретов/чувствительных данных.

---

## Зачем это

**Зелёные тесты ≠ работающая система.** Тесты проверяют то, что ты **догадался** проверить, часто на выдуманных данных и с замоканными границами. Живая приёмка ловит классы, которые тесты структурно не видят:

- реальная форма данных на стыках (не hand-shaped моки);
- реальная конфигурация окружения (env-флаги, порты, роуты, секреты);
- реальные внешние интеграции (API, БД, очереди);
- права доступа и изоляция на живых данных;
- happy-path, который «зелёный» в unit, но падает на реальном запросе.

Правило: **фича не закрыта, пока ты не прошёл реальный сценарий глазами пользователя и не проверил инварианты адверсариально.**

## Дерево выбора слоя проверки

Спроси: **что именно я проверяю?** — и возьми **самый дешёвый слой**, который это ловит. Дорогой живой стенд — только для того, что дешёвые слои структурно НЕ видят.

| Что проверяю | Слой | Стоимость | Достаточно, когда |
|---|---|---|---|
| Логику функции/модуля (чистая обработка, ветвление, расчёт) | **unit** | секунды | Логика изолирована, границы можно замокать честно |
| Рендер компонента / нетривиальное состояние представления | **компонент** | секунды | Ветвление/empty-view/состояние UI в изоляции, без живого бэка |
| Взаимодействие модулей / реальный запрос к хранилищу / роутинг | **integration** | секунды–минуты | Баг живёт на стыке двух модулей или в реальном запросе к хранилищу |
| **Значение ПЕРЕСЕКАЕТ провод** (сериализация/парсинг на границе: snake↔camel, proto/JSON decode, DTO-маппинг) | **контрактный стык** | секунды | Баг живёт ровно в трансформации на границе вход→сеть→выход — самый частый «тихий» класс (см. `./debugging.md`) |
| Полный путь через реальную сборку (API → обработка → хранилище → ответ) | **e2e** | минуты | Нужен весь конвейер, но без живого стенда/внешних систем |
| Реальный сценарий на поднятом окружении (браузер / curl / реальные интеграции) | **живой стенд** | минуты, нужно окружение | То, что видно только на реальной конфигурации/данных/UI |
| «А как это себя ведёт?» без гейта (ручная разведка) | **exploratory** | ручная | Recon. Найденный баг закрывается регресс-тестом слоёв выше |

**Правила выбора:**
- **Никогда не начинай с живого стенда.** Если логику ловит unit — пиши unit; живой прогон доказывает лишь то, что дешёвые слои не видят.
- **Живой стенд не заменяет unit/integration.** Headless-зелёное ≠ live-зелёное, но и живой прогон без нижней подложки хрупок и дорог.
- **Контрактный стык — отдельный дешёвый слой.** Класс «форма разошлась на границе провода» unit не видит (там мок), а живой стенд ловит дорого. Тест ровно на пересечении границы — с РЕАЛЬНОЙ сериализацией — ловит его за секунды.
- **exploratory — только разведка.** Не гейт. Любую находку закрой стандартным тестом.

> **Слои в стеке проекта:** `# ADAPT:` перечисли конкретные раннеры по слоям в [`./stack-specifics.md`](./stack-specifics.md) (unit → компонент → integration → **контрактный стык** → живой стенд → exploratory). Бери самый дешёвый достаточный слой.

## Машинный вердикт живого прогона (exit-коды + failure-артефакты)

Живой/e2e-прогон должен возвращать **машиночитаемый результат**, а не только «посмотрел глазами» — иначе его нельзя вставить в CI/ops-гейт и легко объявить «зелёным» вслепую.

- **Структурированный exit-код.** Прогон завершается стабильным кодом: `0` — все шаги прошли; `1` — assertion-fail (реальный дефект, **в т.ч. security-регресс** — чинить); отдельный код — инфраструктурный сбой окружения (стенд не поднялся / таймаут — это НЕ дефект фичи, а «повтори/почини стенд»). Не сваливай эти классы в один код: «стенд не поднялся» ≠ «фича сломана».
- **Failure-артефакты.** При падении прогон **автоматически** складывает durable-бандл для разбора без повторного воспроизведения: снимок состояния на момент падения (скриншот/DOM для UI, дамп ответа/запроса для API, релевантные логи), номер упавшего шага, фактическое vs ожидаемое. Разбирают потом по артефакту — не гоняют стенд заново вслепую.
- **Content-free stdout.** В stdout — только структурные факты (шаг, ok/fail, деталь), без дампа секретов/PII.

> **Если формального e2e-runner в проекте пока нет:** минимум — curl-сценарий с проверкой HTTP-кодов + integration-кейсы штатного тест-раннера (стабильные exit-коды из коробки). Артефакты падения складывай в scratchpad / логи стенда. Завести e2e-walker — кандидат при старте крупной инициативы.

## Pre-flight — поднять окружение

Перед проходом сценария окружение должно быть **поднято и здорово**.

```bash
# ADAPT: точные команды подъёма стенда и health-check — см. stack-specifics.md / ../ops/local-setup.md (./vendor/bin/sail up -d && ./vendor/bin/sail artisan migrate && pnpm dev)
./vendor/bin/sail up -d && ./vendor/bin/sail artisan migrate && pnpm dev      # инфраструктура (БД/брокер) + backend + frontend
# health-check: каждый сервис отвечает ожидаемым кодом ПЕРЕД сценарием
```

Полный стенд и команды остановки — `../ops/local-setup.md`. Health-check зелёный ПЕРЕД сценарием.

**Не начинай сценарий на неподнятом/нездоровом окружении** — иначе «баг» окажется просто незапущенным сервисом.

### Где поднимать стенд: свой код vs уже смерженное ⛔

Основные порты/БД стенда — это **основной worktree интеграционной ветки** (`develop`): чужой уже смерженный код и **боевая dev-БД** с реальными чувствительными данными (боевые креды БД/S3-MinIO/API-токенов/Cloudflare Tunnel из `.env` наружу не выносить и в тестах не использовать — тесты на `.env.testing`). Прогонять здесь стенд **из своего task-worktree** нельзя.

- **Принимаешь СВОЙ код** из `tasks/<slug>` (фича ещё не смержена) → подними стенд **изолированно**, **даже если работаешь СОЛО**. Причина не только «параллель»: изоляция защищает боевую dev-БД от прогонов незрелого кода и не смешивает твой стенд с общим.

  - **Модуль изоляции окружений в этом профиле ВЫКЛЮЧЕН** — автоматического скрипта клонирования стенда нет, изолируй **вручную**. Минимум: поднимай стенд на **эфемерной БД** (пересоздаваемая пустая база Sail / `.env.testing` с `RefreshDatabase`) и/или **фикстурах**, а НЕ на боевой dev-БД; свой backend/frontend — на отдельном порту. Никогда не гоняй незрелый код своей ветки против общей dev-БД с реальными данными.
- **Основной стенд `develop`** — только для приёмки **уже смерженного** (интеграционная проверка), НЕ для приёмки своего кода из worktree.

## Проход сценария глазами пользователя

Пройди **реальный сценарий** фичи так, как его прошёл бы пользователь — через реальную поверхность (HTTP / браузер / CLI), не через unit-обёртку.

```bash
# Примеры формы (подставь свою):
curl -sS -X POST http://localhost:PORT/api/<endpoint> -d '<payload>' | jq .   # реальный ответ, реальный код
# или: открыть страницу в браузере, пройти флоу кликами
# или: прогнать e2e-скрипт против поднятого окружения
```

Сверься с **Acceptance Criteria** из `spec.md`: каждый AC → наблюдаемый результат на живом прогоне (не «должно работать», а «вот 201 + объект в хранилище»).

## Адверсариальная проверка инвариантов ⛔

Happy-path — половина работы. Проверь **негативы** — то, что должно быть НЕВОЗМОЖНО:

```
□ Чужие данные не видны (запрос под юзером A не отдаёт данные юзера B)
□ Невалидный вход отвергается (битый payload → 4xx, а не 500 и не тихий проход)
□ Права соблюдены (защищённый endpoint без auth → 401/403, не 200)
□ Отсутствующий ресурс → корректный not-found, а не утечка «существует, но нет доступа»
□ Границы значений (пусто / очень большое / спецсимволы) не роняют систему
□ Секреты не в ответе / не в логах (токены, пароли, PII)
```

> **Проектные адверсариальные инварианты:** `# ADAPT:` перечисли их в [`./stack-specifics.md`](./stack-specifics.md) §Инварианты (`Domain не зависит от Infrastructure/Laravel; контроллеры тонкие; бизнес-логика в Application/Domain; доступ к БД через репозитории; Filament Resource без бизнес-логики; валидация во FormRequest/DTO; авторизация через Policies`) — напр. изоляция чувствительных данных по владельцу/тенанту, permissions, capability-гейты скрытых фич (canonical end-to-end, не только меню), корректная работа с датами/таймзонами, маршрут справочников через нужный сервис.

**Deny должен вести себя как «не существует»**, где это уместно (не раскрывать существование недоступного ресурса).

## Протокол «дефект найден»

Нашёл дефект в живой приёмке — **не чини на месте молча**. Дефект = отдельная мини-фича:

1. **Останови приёмку** текущей фичи (она не закрыта).
2. **Заведи фикс** как fix-фичу (полный FEAT-NNN по [`./feature-workflow.md`](./feature-workflow.md), либо trivial-fix, если критерии подходят).
3. **Причину — по [`./debugging.md`](./debugging.md)** (repro → граница → расхождение).
4. **Регрессионный тест** (красный до фикса).
5. **Повтори живую приёмку** после фикса — с самого начала сценария (фикс мог сдвинуть поведение).

Дефект + его фикс фиксируются с тегом класса (см. [`../devlog/README.md`](../devlog/README.md) §Каталог тегов).

## Сводка для приёмки (в impl.md)

По итогу — короткая **«Сводка для приёмки»** в `impl.md` фичи: что именно прогнал живьём и с каким результатом. Не пересказ протокола — только факты приёмки:

```markdown
## Сводка для приёмки

- Окружение: поднято (<команды>), health зелёный.
- Сценарий: <что прошёл> → <наблюдаемый результат> (соответствует AC-1..AC-N).
- Адверсариально: чужие данные не видны ✓ · невалидный вход → 400 ✓ · без auth → 401 ✓.
- Дефекты в ходе приёмки: <нет / FEAT-NNN-fix, закрыт + регресс-тест>.
- Слой(и) проверки: unit + integration + живой прогон (curl/браузер).
```

## Быстрый чеклист

```
[ ] Выбран самый дешёвый достаточный слой (не начал с живого стенда; контрактный стык — отдельная ступень)
[ ] Окружение поднято и health-check зелёный
[ ] Свой код принимается на ИЗОЛИРОВАННОМ стенде (не на общей dev-БД) — даже соло
[ ] Реальный сценарий пройден через реальную поверхность (curl/браузер/e2e)
[ ] Прогон вернул машинный вердикт (структурный exit-код; при падении — failure-артефакт)
[ ] Каждый AC подтверждён наблюдаемым результатом
[ ] Адверсариальные инварианты проверены (чужое не видно / невалид отвергнут / права соблюдены)
[ ] Дефекты → отдельная fix-фича + регресс-тест + повторная приёмка
[ ] «Сводка для приёмки» записана в impl.md
```
