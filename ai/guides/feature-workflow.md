# Гайд: Реализация функционала через фичу

> **Аудитория:** AI-ассистент и разработчик проекта `cbook`.
> **Связанные документы:** `../architecture.md` (архитектура, §0 роутер, §8 гигиена), `../memory.md` (текущий статус), `../devlog/README.md` (структура артефактов), `../adr/` (архитектурные решения), `./stack-specifics.md` (команды и инварианты стека).

---

## ⛔ Гигиена клиентского репозитория (действует на КАЖДОМ шаге)

Всё, что попадает в клиентские репы (`cbook`, `(отсутствует)`, ...), не должно нести следов этой системы. Полное правило — `../architecture.md` §8. Кратко:

- **Ноль упоминаний** системы (`ai/`, `study-cbook-ai`, FEAT-номера, спеки, агенты/ИИ, оркестраторы) в коде, комментариях, коммитах, ветках, MR.
- **Комментарии в коде** — только «как писал бы человек», по стилю окружения, без ссылок на внутренние документы.
- **Временные пометки** — только маркером `~wip~`; ВСЕ удаляются до завершения фичи (pre-commit хук блокирует их).
- **Коммит — только через `scripts/commit.sh`**; `git push` агенту запрещён (доставка — пользователь).
- **Ветки** — `feat/<понятный-slug>` без номеров; маппинг FEAT-NNN ↔ ветка — в `../devlog/features/README.md`.
- **Коммит-сообщения** — формат команды `<type>: <описание> (conventional commits; type ∈ feat|fix|chore|refactor|docs|test|style|perf|build|ci)` (источник истины — `FORMAT_RE` в `scripts/commit.sh`).
- **Финальный DoD** — «ревью чистоты» свежим субагентом без доступа к `ai/` (Шаг 12).

---

## Зачем этот процесс

Хаотичная реализация без планирования — главная причина: несогласованностей между компонентами, нарушений архитектурных инвариантов, тихих регрессий, техдолга, который блокирует следующие фичи.

Этот гайд — **обязательный алгоритм** для любой нетривиальной работы.

## Шаг 0 — Когда нужна фича

> **Нужна бронь?** Забронируй фичу (`./scripts/coord.sh book <slug>` — атомарно выделит FEAT-номер,
> индекс, порты и БД, исключит гонку slug'ов), если выполнено ХОТЯ БЫ ОДНО:
> — в workspace трудится **больше одного агента** (параллель); ИЛИ
> — тебе нужна **изолированная живая приёмка своего кода** (свои порты + клон-БД вместо общей
> dev-БД с чувствительными данными — см. [`./live-acceptance.md`](./live-acceptance.md), «Где поднимать стенд»),
> даже если ты работаешь СОЛО.
> До старта в параллели — прочитай [`./coordination.md`](./coordination.md).

### Создавать фичу ОБЯЗАТЕЛЬНО если:
- Меняется **2+ файла в разных пакетах / модулях**
- Добавляется/меняется **новая сущность** (модель данных, миграция)
- Изменение **затрагивает контракты** (API-схема, типы frontend), которыми пользуются другие части
- Добавляется **автоматизация** (фоновая задача, management-команда, cron)
- Меняется **бизнес-процесс**
- Задача требует **более 30 минут работы**
- Затрагиваются **миграции БД**, permissions/роли, чувствительные данные (`аутентификация/сессии (Laravel auth), файловое хранилище (S3/MinIO), доступ к БД (Eloquent + репозиторный слой), Filament-панель (политики доступа)`)

### Можно без фичи (inline change):
- Фикс опечатки / однострочный bugfix в одном файле
- Обновление документации / комментариев
- Переименование переменной / рефактор внутри одного файла
- Косметика UI без изменения контрактов

### Trivial-fix shortcut (канал `devlog/YYYY-MM-DD.md`)

Если правка удовлетворяет ВСЕМ критериям — можно **не создавать FEAT-NNN директорию**, а зафиксировать одной строкой в `../devlog/YYYY-MM-DD.md` под `## Quickfixes`:

**✅ Критерии quickfix (ВСЕ должны выполняться):**
- 1-2 файла изменяются
- <50 LOC diff
- НЕ затрагивает контракты (API / frontend-типы)
- НЕ затрагивает схему БД (миграции)
- НЕ затрагивает keystone-контракт (см. ADR-таблицу `../architecture.md` §10)
- НЕ требует обновления `../architecture.md` §0/§10
- НЕ трогает permissions / чувствительные данные (`аутентификация/сессии (Laravel auth), файловое хранилище (S3/MinIO), доступ к БД (Eloquent + репозиторный слой), Filament-панель (политики доступа)`)

**❌ FEAT-NNN ОБЯЗАТЕЛ даже для trivial, если хотя бы одно из:**
- Есть (или должен быть) регрессионный тест → smoke показал баг
- Затронут §0/§10 `../architecture.md` (новый пакет/сервис/контракт)
- Затронут keystone-контракт (ADR в §10)
- Затронуты permissions / изоляция чувствительных данных
- Изменение выкатывается на прод → нужен живой smoke

**Канал:** одна строка в `../devlog/YYYY-MM-DD.md`:

```markdown
# 2026-07-16

## Решения
- ...

## Quickfixes

- quickfix-typo-readme: опечатка в README (1 файл, 8 LOC)
```

**Ветка:** `feat/<slug>` (без номера). Коммит через `scripts/commit.sh`. **§8 гигиена действует.** Quickfix **НЕ освобождает** от гейтов (минимальный набор тесты/typecheck/lint — что применимо; команды — [`./stack-specifics.md`](./stack-specifics.md)).

> **Мотивация:** некоторые правки настолько мелкие, что полный FEAT-NNN — over-формализация. Quickfix использует существующий дневной лог. Жёсткие численные критерии (1-2 файла, <50 LOC) легко проверяемы.

## Шаг 1 — Изучение контекста

### Step-0 (для свежего worktree) — ПЕРВЫМ действием

Свежий worktree создаётся `./scripts/task.sh new <slug>` (ветка `feat/<slug>` от `origin/develop`, папка `tasks/<slug>`). Прежде чем читать файлы проекта:

```bash
# ВЕРДИКТ свежести базиса ПЕРВЫМ: не работать на стале молча.
git fetch origin develop                # или ./scripts/sync.sh
# сравни HEAD worktree с origin/develop и дай явный вердикт FRESH/STALE одной строкой

# worktree уже от origin/develop; при рассинхроне — подтянуть базис явно:
git merge origin/develop --no-edit

# восстановить окружение фичи (deps/codegen/миграции):
# ADAPT: команды восстановления зависимостей и прогона миграций — ./scripts/sync.sh && ./scripts/status.sh, см. ./stack-specifics.md §venv

# завершить ВЕРДИКТОМ одной строкой: "Step-0 OK: merge ✓ deps ✓ migrate ✓"
```

> Нет отдельного скрипта проверки свежести — вердикт свежести (FRESH/STALE) даёшь сам, явной строкой,
> по результату `git fetch origin develop` (или `./scripts/sync.sh`).

**Вердикт обязателен:** Step-0 заканчивается **одной строкой-вердиктом**. Детали команд — [`./stack-specifics.md`](./stack-specifics.md).

**Симптом сталого базиса:** если в worktree нет prereq-кода/спеков/keystone, которые ТОЧНО смержены в `develop` — это сталый базис, сделай `git merge origin/develop`; НЕ интерпретируй как «фича не начата».

### Контекстные файлы для чтения

**Перед написанием spec обязательно прочитать:**

```
1. ai/architecture.md            — архитектура, стек, §0 роутер (первым), §8 гигиена
2. ai/memory.md                  — текущий статус, что сделано, открытые задачи
3. ai/devlog/features/           — существующие фичи → следующий FEAT-NNN
4. ai/adr/                       — архитектурные решения (при сомнениях)
5. cbook/CLAUDE.md   — правила клиентского репо (ОБЯЗАТЕЛЬНО)
```

Плюс по типу фичи (конкретные пути/слои — [`./stack-specifics.md`](./stack-specifics.md)):
- **Backend** → `./stack-specifics.md` §Backend + похожая сущность/сервис как паттерн.
- **Frontend** → `./stack-specifics.md` §Frontend + похожая страница/компонент.
- **Миграции** → раздел миграций `./stack-specifics.md` (роутинг БД, `.using()` и т.п.).
- **User-visible изменение** → `user-visible изменения отражать в клиентском CLAUDE.md / README проекта` (правило пользовательской документации/help-центра).

**Ответь себе на вопросы:**
- Какие модули / слои задействованы?
- Нужны ли миграции БД? Затрагивают ли общие/shared-контуры?
- Затрагиваются ли permissions / чувствительные данные? (→ обязательные тесты)
- Есть ли похожие сущности/фичи, с которых копируется паттерн?
- Меняется ли user-visible поведение? (→ пользовательская документация)

Найди похожие завершённые фичи в `../devlog/features/` и прочитай их `spec.md` — это готовые паттерны.

## Шаг 2 — Декомпозиция

### Критерии необходимости разбивки

| Признак | Почему разбить |
|---------|----------------|
| Реализация затрагивает 3+ слоя/пакета одновременно | Риск рассинхронизации |
| Часть А нужна другим фичам независимо от Б | Блокирует параллельную работу |
| Есть чёткая граница «foundation + feature» | Foundation должна стабилизироваться |
| Spec занимает > 200 строк | Сигнал о переусложнении |
| Разные части имеют разные риски | Изолировать нестабильное |

### Паттерн декомпозиции

```
❌ FEAT-020-full-feature       (модель + API + permissions + UI + миграция + тесты)
✅ FEAT-020-feature-backend    (модель, миграция, API, permissions, backend-тесты)
✅ FEAT-021-feature-ui         (скрытый раздел, форма, клиент, integration)
```

**Правило — одна фича, одна ответственность:** каждая фича решает одну проблему, оставляет систему в рабочем состоянии, не создаёт «полу-готовых» состояний.

### Порядок работы при нескольких фичах: Specs First

Если после декомпозиции 2+ фичи — сначала напиши спецификации для **всех** фич цепочки, потом реализуй по одной:

```
✅ specs first: spec FEAT-020 + 021 + 022 → тройная проверка ВСЕХ → реализация по одной
❌ spec 020 → impl → spec 021 → impl …
```

**Почему:** свежий контекст всей картины, раннее обнаружение конфликтов контрактов/миграций, корректные границы.

**Исключение:** фичи полностью независимы (разные пакеты, нет общих контрактов) — допустимо spec→impl по одной.

> **Масштаб ADR-инициативы** (напр. крупный блок из многих фич): specs-first становится **фазовым гейтом**. Канон — [`./adr-execution.md`](./adr-execution.md) Часть G.

## Шаг 3 — Нейминг и директория

```
ai/devlog/features/FEAT-NNN-slug/
```

- `NNN` — следующий сквозной порядковый номер (нумерация общая на все репозитории проекта)
- `slug` — 2-4 слова через дефис, kebab-case

```bash
ls ai/devlog/features/ 2>/dev/null | sort | tail -5
```

Структура фичи:

```
FEAT-NNN-slug/
├── spec.md      ← создаём СЕЙЧАС (до реализации)
├── impl.md      ← создаём ПОСЛЕ реализации и прохождения тестов
└── retro.md     ← опционально, для крупных фич
```

> `impl.md` и `retro.md` создаются только по факту.

**Обязательное поле spec «Затрагиваемые репозитории»** — единый контекст покрывает несколько репо, поэтому явно указывай, какие репозитории затронуты. Если **несколько** — заведи бронь и worktree **на каждый репо отдельно** (рецепт мультирепной фичи в §3.5): несколько репо в spec ⇒ несколько броней/worktree, несколько MR.

> **Однорепный профиль (M1 контуры совпадают / мультирепность выключена):** поле «Затрагиваемые репозитории» вырождается в один репозиторий — оставь его как явную констатацию, мультирепный рецепт §3.5 не применяется.

## Шаг 3.5 — Изоляция: ветка + worktree через `task.sh` (по умолчанию ОБЯЗАТЕЛЬНО)

Каждая фича = **отдельная ветка в отдельном worktree**, создаётся штатным механизмом workspace (`scripts/task.sh`, ADR-004), а НЕ `.claude/worktrees`.

### Механизм

```bash
# создать ветку feat/<slug> от develop + worktree tasks/<slug>:
./scripts/task.sh new <slug>                    # база по умолчанию develop
./scripts/task.sh new <slug> main    # хотфикс от прода

# подключить существующую ветку:
./scripts/task.sh add <ветка>

# список worktree:
./scripts/task.sh ls

# удалить worktree (ветка остаётся) — зона оркестратора/пользователя после доставки:
./scripts/task.sh rm <имя-папки>
```

- **Имя ветки — `feat/<понятный-slug>` без FEAT-номера** (§8). Соответствие FEAT-NNN ↔ ветка ведётся в `../devlog/features/README.md`.
- В основных worktree (`develop` / `main`) фичи **не пилить** — только интеграция/сравнение.

### Когда можно без worktree
- **Trivial-fix** (1-2 файла) — допустимо в `tasks/` при отсутствии параллельной работы; в основном worktree — нет.
- **Docs-only правки в `ai/`** — прямо в `ai/` (это отдельный репозиторий `study-cbook-ai`, кода клиента не касается).

### Когда worktree ОБЯЗАТЕЛЕН
- Любая нетривиальная фича, параллельная работа нескольких агентов, крупный ADR-блок.

### Step-0 в свежем worktree
Сразу после `task.sh new` — выполни Шаг 1 Step-0 (fetch+merge `origin/develop`, восстановить окружение, миграции). Worktree создан от `origin/develop` на момент запуска, но параллельные ветки могли уйти дальше.

### Изолированное окружение при параллельной работе
Если фича забронирована (`coord.sh book`) — после `task.sh new` изолируй окружение вручную: свои
порты (по индексу брони — см. [`./coordination.md`](./coordination.md)), эфемерная тестовая БД в
Sail и/или `.env.testing` (`RefreshDatabase`). Нет отдельного скрипта для этого — правило простое:
никогда не гоняй невлитый код по общей dev-БД с чувствительными данными. Подробности и жизненный
цикл координации — [`./coordination.md`](./coordination.md).

> Изолированную приёмку своего кода (Шаг 8 / [`./live-acceptance.md`](./live-acceptance.md)) держи
> на эфемерной БД/фикстурах — не гоняй свой невлитый код по общей dev-БД с чувствительными данными.

### Фича, затрагивающая несколько репозиториев

Единый FEAT покрывает несколько репо, но **инструменты изоляции — пер-репо** (worktree и бронь заводятся на конкретную репу). Рецепт «один FEAT = несколько репо»:

- **Один FEAT-NNN и одна папка** `devlog/features/FEAT-NNN-slug/` (общий spec/impl на всю фичу).
- **Бронь и worktree — ПО ОДНОЙ НА РЕПО** (разные порты/БД, разные ветки):
  ```bash
  # основной репо:
  ./scripts/coord.sh book <slug>
  ./scripts/task.sh new <slug>
  # второй репо:
  ./scripts/coord.sh book <slug>-<repo2> --repo (отсутствует)
  ./scripts/task.sh --repo (отсутствует) new <slug>-<repo2>
  ```
- **В spec-поле «Затрагиваемые репозитории»** перечисли **все** затронутые репо — это ровно те репо, под которые ты завёл отдельные брони/worktree.
- **Доставка — отдельным MR на каждый репо** (пользователь): каждая ветка `feat/<slug>` мержится в свой `develop`.
- Общие артефакты фичи в `study-cbook-ai` (spec/impl) — как обычно через `./scripts/ai-commit.sh`.

> Координация двух броней одной фичи и лимиты ресурсов — [`./coordination.md`](./coordination.md).

### ⚠️ `git stash` ЗАПРЕЩЁН в worktree

`.git` **ОБЩИЙ** на все worktree (общий bare-репозиторий): `git stash pop` в одном worktree вытащит **ЧУЖОЙ** stash параллельного агента (реальный риск потери WIP). Временное состояние — только **commit в свою ветку** (через `scripts/commit.sh`, потом аменд/сквош) или файл в scratchpad. Обнаружил чужой stash — не снимай, сообщи оркестратору/пользователю.

## Шаг 4 — Написание spec.md

### Обязательная структура

```markdown
# FEAT-NNN: Название

## Статус: SPEC

## Затрагиваемые репозитории
<репо-1> (backend / frontend) | <репо-2> | несколько   ← ОБЯЗАТЕЛЬНОЕ поле
# «несколько» ⇒ отдельная бронь + worktree на каждый репо + отдельный MR (§3.5, мультирепный рецепт)

## Цель
Одно-два предложения: ЧТО делаем и ЗАЧЕМ.

## Контекст
Текущее состояние. Почему нужно сейчас. Связь с предыдущими фичами.
Ссылки на ТЗ / бизнес-процессы / ADR.

## Acceptance Criteria
Список конкретных, проверяемых утверждений в виде наблюдаемого результата.
- [ ] «POST /api/... с валидным payload → 201 + запись в БД»
- [ ] «Скрытый раздел доступен только по прямому URL, в меню не виден»
- [ ] «Роль X получает право `entity:create`, роль Y — 403»

## Технический дизайн
# ADAPT: подсекции дизайна под слои вашего стека (Backend / Frontend / …) — см. ./stack-specifics.md.
# Обязательно фиксировать: контракты/схемы (модели, сериализаторы, типы) ДО бизнес-логики;
# миграции (роутинг БД, обратная совместимость); permissions/роли; фоновые задачи; capability-гейты.

## Тесты

**Добавить:** `path/to/test_*` — что проверяет, ожидаемый результат.
**Обновить:** — что изменится в assertion-ах и почему.
**Удалить:** — почему тест становится неактуальным.

> Требование: для permissions и чувствительных данных — **обязательны** позитивные И **негативные** тесты (чужой доступ → 403, изоляция данных).

## Типизация/качество (минимальный набор гейтов)
- **Минимальный набор гейтов прогоняется вручную** (нет отдельного quality-скрипта): тесты (Pest),
  typecheck (PHPStan/Larastan), lint (Pint) — сериализуй тяжёлые прогоны через `./scripts/gate.sh`.
- **Типы API — из контракта** (кодогенерация из схемы), не рукописные.
- **Новый код чист**: 0 новых подавлений типов/линтера, даже внутри legacy-модулей; касание legacy → характеризующие тесты предусловием.

## Безопасность
Заполнять явно (если угроз нет — «Нет новых поверхностей атаки»).
- **Доступы:** какие роли получают доступ к новому API? Нет ли методов без authz? least privilege.
- **Данные:** какие поля — чувствительные? Фильтрация по владельцу/арендатору в запросах к БД?
- **Валидация:** все внешние входы валидируются до бизнес-логики?

## Пользовательская документация (user-visible изменения отражать в клиентском CLAUDE.md / README проекта)
- Меняется ли user-visible поведение → нужна ли правка публичной документации / help-центра?

## Зависимые файлы для изменения
Таблица: файл → тип изменения.

## Что НЕ входит в эту фичу
Явно исключить scope creep.

## Оценка сложности
Низкая / Средняя / Высокая. Ключевые риски.
```

### Правила хорошего spec

**Цель** — одна чёткая фраза. **Acceptance Criteria** — наблюдаемый результат, не действие:
```
❌ «Реализовать проверку прав на запись»
✅ «POST /api/... под ролью без права → 403 (не 200, не 500)»
```
**Технический дизайн** — конкретные имена файлов/сущностей/контрактов. **Тесты** — конкретные тест-кейсы.

## Шаг 4.5 — ADR-решение (если фича требует архитектурного выбора)

Нужен, только если фича делает **неочевидный архитектурный выбор** (выбор между технологиями/подходами, новый паттерн, замена принятого решения — критерии в [`../adr/README.md`](../adr/README.md) «Когда создавать ADR»). Обычной фиче ADR **не нужен** — пропусти шаг.

> **decision-ADR ≠ ADR-инициатива.** Здесь — **одна карточка** `adr/NNN-slug.md` под **одну** фичу. Крупный блок из десятков фич с оркестратором — это [`./adr-execution.md`](./adr-execution.md), не сюда.

1. **Номер.** `./scripts/coord.sh book <slug> --adr` (выделит FEAT- и ADR-номер атомарно), либо — вне параллели — следующий свободный сквозной номер по `ls ai/adr/`.
2. **Где создать.** `ai/adr/NNN-slug.md` — это **`study-cbook-ai`** (база знаний), **НЕ клиентский код** (§8: в клиентские репы ADR не кладём). Формат карточки — по [`../adr/README.md`](../adr/README.md) (статус, контекст, варианты, решение, последствия). Начальный статус — `Принят`.
3. **Коммит.** Отдельным коммитом через `./scripts/ai-commit.sh "DOCS / ADR-NNN: <решение>" ai/adr/NNN-slug.md` (общий артефакт `study-cbook-ai` — под локом shared-docs, не через `commit.sh`).
4. **Ссылка в spec.** В `spec.md` («Контекст» или «Технический дизайн») сошлись на `adr/NNN-slug.md` — почему выбран этот подход.
5. **Смена статуса.** Когда фича реализована — переведи статус ADR `Принят → Реализован` в Шаге 10 (вместе с обновлением `../architecture.md` §10 ADR-таблицы).

## Шаг 5 — Тройная проверка spec ⚠️ ОБЯЗАТЕЛЬНО

После написания spec.md — **три последовательные итерации**.

### Итерация 1: Полнота
```
□ Цель понятна без контекста?
□ Acceptance Criteria покрывают ВСЕ аспекты (backend + frontend + тесты + пользовательская дока)?
□ Поле «Затрагиваемые репозитории» заполнено?
□ Все затронутые файлы перечислены в «Зависимые файлы»?
□ Нет scope creep?
□ Контракты/схемы (модели, сериализаторы, типы) зафиксированы до бизнес-логики?
□ Новые env-переменные перечислены? Миграции описаны (с учётом общих/shared-контуров)?
□ Обратная совместимость API — что ломается для существующих клиентов?
```

### Итерация 2: Логика, связи, архитектура
```
□ Нет противоречий между разделами (дизайн ≠ AC)?
□ Нет циклических зависимостей между фичами?
□ Архитектурные инварианты соблюдены:
   # ADAPT: перечень инвариантов проекта — Domain не зависит от Infrastructure/Laravel; контроллеры тонкие (без бизнес-логики); бизнес-логика в Application/Domain; доступ к БД через репозитории; Filament Resource без бизнес-логики; валидация во FormRequest/DTO; авторизация через Policies, канон — ./stack-specifics.md §Инварианты
   • новый код строгий по baseline-diff (новый файл/новая строка чисты, 0 подавлений типов), даже внутри legacy
   • типы API — из контракта (кодогенерация), не рукописные
   • изменение legacy — предваряется характеризующими тестами (фиксируют текущее поведение до правки)
   • доступ к справочным/общим данным — через контрактный клиент, не прямыми запросами к shared-БД
   • миграции --database-aware; data-миграции пишут в явную БД
   • capability-гейт canonical end-to-end (не по имени окружения)
□ Новые тесты не конфликтуют с существующими (порты, имена БД, контуры golden/sandbox)?
□ Есть ли фаза «удаление устаревшего кода», если фича заменяет старое?
```

### Итерация 3: Безопасность ⛔
```
□ Доступы/authz
   • Каждый новый endpoint имеет явную authz-политику? least privilege?
□ Аутентификация и авторизация
   • Новые endpoint проверяют auth/permission перед бизнес-логикой?
□ Безопасность данных
   • Запросы фильтруются по владельцу/арендатору (изоляция чувствительных данных)?
   • Нет хранения секретов/токенов в plaintext? Миграции обратно совместимы?
   • Нет прямой конкатенации user input в raw SQL (используем ORM/параметризацию)?
□ Безопасность кода
   • Секреты только из env, не хардкод? В логах нет токенов/паролей/чувствительных данных?
   • Внешние данные валидируются до записи в БД?
□ Гигиена репозитория (§8)
   • В планируемом коде/комментариях нет упоминаний системы/FEAT/агентов?
```

Если найдены проблемы — **исправь spec** перед реализацией.

## Шаг 7 — Реализация

### 7.1 Порядок изменений (снизу-вверх, НИКОГДА не в обратном)

Порядок — от контракта/схемы к API/UI; конкретные шаги под стек — [`./stack-specifics.md`](./stack-specifics.md):

```
# ADAPT: порядок создания сущности под ваш стек — миграция → Eloquent-модель → доменный слой (сущность/DTO/VO) → сервис (Application) → контроллер + Inertia response → тесты (Pest) / Inertia page → компонент Vue → composable/store → типы (TS) → тесты, ./stack-specifics.md
Backend (обобщённо):
1. Модель + ограничения + permissions-перечисление
2. Миграция — проверить роутинг БД / общие контуры; data-миграции пишут в явную БД
3. Сериализаторы + бизнес-логика (services/)
4. API-обработчики + регистрация маршрутов
5. Роли/permissions → справочные данные
6. Фоновые задачи / management-команды (если нужны)
7. Тесты — параллельно с 3-5

Frontend (обобщённо):
1. Типы (types-first)
2. Клиент/composable к API
3. Страницы / роуты
4. Компоненты (из дизайн-системы проекта)
5. Тесты — параллельно
```

**Никогда не менять обратный порядок** — изменение контракта после кода гарантирует рефакторинг.

### 7.2 Атомарные изменения
- Один логический блок за раз; тесты **после каждого блока**; сломался → исправить до следующего.

### 7.3 Чеклист по ходу реализации

```
# ADAPT: стек-специфичные пункты (структура сущности, дизайн-токены, слой доступа к данным) — ./stack-specifics.md
Универсальное:
□ Контракты/схемы зафиксированы ДО кода, потребляющего их
□ Новый endpoint → права выставлены явно (не default-open)
□ Адресные/справочные данные → через контрактный клиент, не прямыми запросами к shared-БД
□ Новые env → в .env.example (маской), не реальным значением
□ Никаких ~wip~ маркеров в финальном состоянии
□ Комментарии — «как писал бы человек», без следов системы (§8)
```

### 7.4 Security checklist по ходу реализации

```
□ Новый защищённый endpoint → есть явное право (не default-open)
□ Новый DB-запрос с чувствительными данными → фильтр по владельцу/арендатору
□ Новый DB-запрос → параметризация ORM, не raw SQL с user input
□ Новый endpoint → валидация входа до бизнес-логики
□ Секреты → только env, не хардкод; логи без токенов/паролей/чувствительных данных
□ Новые env с секретами → в .env.example с маской
```

Каждый ключевой AC — подтверждён живьём.

> ⚠️ **Дефект, пойманный живой приёмкой, закрывается фиксом И НЕ-ВАКУУМНЫМ регресс-тестом** нужного уровня (red ДО фикса → green после). «Просто починил без теста» — НЕ DoD. После фикса — можно ли закрыть класс **структурно** (lint / типовой инвариант / completeness-тест)?

## Шаг 12 — Финализация: коммит + «ревью чистоты» (доставка — пользователь)

> ⚠️ **Отличие от дефолта:** агент НЕ пушит и НЕ мержит в `develop`. Доставка (push + MR в репозиторий клиента, merge) — **пользователь**.

После прохождения всех гейтов и обновления связных документов:

```bash
# 1. Убрать ВСЕ ~wip~ маркеры:
grep -rn '~wip~' <изменённые-пути>    # должно быть пусто

# 2. Коммит в СВОЮ ветку — ТОЛЬКО через обёртку (сканер следов + формат сообщения; гейты — Шаг 8):
./scripts/commit.sh "<type>: <описание> (conventional commits; type ∈ feat|fix|chore|refactor|docs|test|style|perf|build|ci)"   # формат сообщений — источник истины FORMAT_RE в commit.sh
#   (git push агенту ЗАПРЕЩЁН — см. §8)

# 2.5 После КАЖДОГО коммита в клиентский репо — разбор «почему» в ai/devlog/commits/<repo>/
#   по шаблону (ADR-009): один markdown на коммит, ключ as-authored hash, два уровня (инженеру/новичку).
#   Можно писать сразу или пачкой в конце фичи; коммит разбора — через ai-commit.sh (это study-cbook-ai, не клиент).
#   Конвенция и шаблон: ../devlog/commits/README.md + ../devlog/commits/_template.md.

# 2.6 НЕЗАВИСИМОЕ по-коммитное ревью (ADR-010) — ОБЯЗАТЕЛЬНО до merge/доставки, ДРУГОЙ агент и роль:
#   разбор (2.5) = автор объясняет «почему»; ревью = независимый агент ищет «корректно ли» (Verdict).
#   Оркестрированный режим — ревьюера запускает оркестратор (вход приёмки B.2 гайда adr-execution).
#   СОЛО-режим — ты автор, ревьюером быть не можешь: запусти СВЕЖИЙ субагент-ревьюер (Opus 4.8, чистый
#   контекст) на свои коммиты, отработай находки фикс-коммитами, только потом «готово к доставке».
#   Полный процесс ревьюера: ../guides/commit-review.md. Каждый коммит → <short-hash>-review.md + строка реестра.
```

```bash
# 3. Финальный DoD — «ревью чистоты»:
#    свежий субагент БЕЗ доступа к ai/ читает `git diff origin/develop...HEAD`
#    как внешний ревьюер: ищет следы системы (ai/, FEAT, спеки, агенты, ~wip~),
#    несоответствие стилю окружающего кода, чужой стиль комментариев.
```

**Правила:**
- **`git push` / merge / MR — только пользователь.** Агент останавливается на локальном коммите + вердикте «ревью чистоты».
- **worktree cleanup** (`./scripts/task.sh rm <slug>`) — зона оркестратора/пользователя ПОСЛЕ доставки; НЕ удаляй worktree до доставки (можно потерять незапушенное).
- **Тирдаун окружения:** если поднимал изолированный стенд вручную (эфемерная тестовая БД Sail /
  `.env.testing`) — снеси её сам после доставки ИЛИ при отмене фичи (мультирепная — по каждой броне).
- Если в ходе работы появилась новая **смежная фича** — **СТОП**, переключиться на новый FEAT-NNN.
- **Честный статус:** фича «✅ готова» только ПОСЛЕ **смерженного MR** в репозитории клиента + зелёных локальных гейтов. «Код написан, тесты в ветке зелёные, ревью чистоты пройдено» — это `🚧 передано пользователю на доставку`, не `✅`.

### Merge-дисциплина при параллельной работе (несколько агентов/веток)

Соло-фича мержится/доставляется пользователем. При параллельных ветках — координация по [`./adr-execution.md`](./adr-execution.md) Часть H. Минимум всегда:

```

```

### Порядок нарушен
```
❌ Написать API-обработчик → потом изменить модель → рефакторинг
✅ Модель/миграция/контракт первыми → потом обработчики
```

### Бизнес-логика в контроллере/Filament Resource
```
❌ RecipeController@update валидирует, пересчитывает рейтинг и рассылает уведомления прямо в методе
✅ Тонкий контроллер вызывает сервис Application-слоя (RecipeService::update), логика — там
```

### Eloquent-запрос напрямую в контроллере
```
❌ Recipe::where('user_id', $id)->get() в контроллере/Filament Resource
✅ Запрос инкапсулирован в репозитории (RecipeRepository), контроллер зовёт репозиторий/сервис
```

### Нет проверки владельца рецепта
```
❌ $recipe->update($data) без $this->authorize('update', $recipe)
✅ authorize() до бизнес-логики + негативный Pest-тест «чужой пользователь → 403»
```

### N+1-запрос без eager load
```
❌ foreach ($recipes as $r) { $r->ingredients; }  // отдельный запрос на каждый рецепт
✅ Recipe::with('ingredients')->get()
```

❌ defineProps<{ data: any }>()  /  прямой fetch() на сторонний хост из компонента
✅ defineProps<{ recipe: Recipe }>() (типизированный интерфейс) + данные только через Inertia-пропсы
```

```
