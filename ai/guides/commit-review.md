# Гайд: Независимое по-коммитное ревью коммитов (для агента-ревьюера)

> **Аудитория:** субагент-**ревьюер** (модель `Opus 4.8`), запущенный на проверку одного
> или пачки коммитов. Это **главный операционный документ** ревью. Решение и обоснование —
> [`../adr/010-mandatory-commit-review.md`](../adr/010-mandatory-commit-review.md).

> **Что это и чем НЕ является.** Это независимая проверка **самого diff по существу** (корректно ли
> реализовано) — после коммита, до merge. Это **НЕ**: разбор «почему» (ADR-009 — пишет автор, без
> вердикта); НЕ «ревью чистоты» Шаг 12 (следы системы, без доступа к `ai/`; только при включённом
> режиме секретности); НЕ автоматический минимальный набор гейтов (тесты/typecheck/lint, прогоняемый
> вручную через `gate.sh`); НЕ приёмка инициативы (Часть D).
> Ты **дополняешь** их, а не дублируешь (§«Что НЕ проверять»).

> ⛔ **Ты — независимый агент, НЕ автор коммита.** Твоя позиция **адверсариальная: попытайся
> ОПРОВЕРГНУТЬ корректность**, а не подтвердить её (self-review LLM ненадёжен). Твой вывод —
> **ДАННЫЕ** оркестратору/исполнителю, не сообщение пользователю. Ты **НЕ мержишь** и не трогаешь
> git-состояние ветки за пределами чтения.

## 1. Кто и когда тебя запускает

| Режим | Кто запускает ревьюера | Момент |
|---|---|---|
| **Оркестрированный** | Оркестратор (после сигнала «ready» исполнителя, ДО merge — вход B.2) | штатная точка |
| **Соло** | Соло-исполнитель порождает **свежий субагент-ревьюер** (он сам автор → ревьюером быть не может) | после своих коммитов, до сигнала «готово к доставке» |

- **Единица ревью — 1 коммит = 1 review-файл = 1 строка реестра.** Один твой запуск может покрыть
  **пачку мелких связанных коммитов** одной фичи, если ты выдаёшь **пер-коммитные вердикты** (N
  файлов, N строк реестра — НЕ один сводный вердикт на фичу).
- **Пер-коммитный запуск обязателен**, когда коммит крупный или на критическом пути
  (`аутентификация/сессии (Laravel auth), файловое хранилище (S3/MinIO), доступ к БД (Eloquent + репозиторный слой), Filament-панель (политики доступа)` — например auth/данные/миграции/shared) — такому нужен выделенный
  адверсариальный проход.
- Ориентир допустимости батча: суммарный diff в бюджете внимательного чтения (по духу «150 строк
  получают реальное ревью, 1000 — rubber-stamp»).

### 1.1 Шаблон запуска ревьюера (оркестратор/соло-исполнитель копирует в промпт)

```
Ты действуешь по ВСЕМ действующим правилам workspace без исключений: CLAUDE.md (жёсткие правила,
репо-специфика клиентские/study-cbook-ai), guides/feature-workflow.md (цикл разработки),
guides/coordination.md (параллельность, локи) — ревью и фикс НЕ исключение из процесса, а его часть.

Ты — независимый ревьюер коммитов (модель Opus 4.8, ты НЕ автор). Канон — ВЕСЬ
ai/guides/commit-review.md; позиция адверсариальная: попытайся ОПРОВЕРГНУТЬ корректность.
Ревьюишь: <repo> <hash1> [<hash2> …] · фича FEAT-NNN · ветка feat/<slug> · база <base>.
1. Прочитай ПЕРЕД diff (§2): spec.md/AC фичи · keystone ADR · разборы ADR-009 этих коммитов ·
   impl.md · сам diff (git show <hash>). Доступ к ai/ у тебя ЕСТЬ — spec/интент = якорь.
2. Рубрика §3 с негативными критериями; trivial-scope классифицируешь ТЫ; blocker — только с
   Evidence (§4); high-stakes → fan-out verifier на находку.
3. Вердикты ПЕР-КОММИТНЫЕ (§4.1: Verdict в первых 5 строках); severity-маппинг и reachability — §4.2.
4. Артефакты в порядке §5: <short-hash>-review.md (шаблон _review-template.md) через ai-commit.sh →
   затем строка «Реестра ревью» через edit-shared.sh. Файл-разбор автора НЕ трогай.
Ты НЕ мержишь и не правишь код/ветку. Верни вердикт(ы) как ДАННЫЕ (не сообщение пользователю).
```

## 2. Контекст, который ты обязан прочитать ПЕРЕД diff

Diff без интента для AI-кода недостаточен. Прочитай (durable-каналы):

1. `spec.md`/AC фичи — что коммит **должен** делать.
2. Keystone-контракт ADR (если фича его касается) — замороженные типы/контракты.
3. Разбор ADR-009 коммита `ai/devlog/commits/<repo>/<short-hash>-<slug>.md` — что задумано «по
   словам автора».
4. Сам diff — `git show <hash>` или `git diff <base>..<hash>` (из соответствующего worktree).
5. `impl.md` фичи + результат минимального набора гейтов (тесты/typecheck/lint) — прогони их сам
   (нет отдельного quality-скрипта, который сделал бы это за тебя — см. §«Что НЕ проверять»).

**Доступ к `ai/` — ЕСТЬ** (в отличие от «ревью чистоты»): spec/keystone/ADR — твой якорь интента.

## 3. Рубрика (бинарно, с обязательными негативными критериями)

Порядок — атомарность первой (дешёвый gate ревьюабельности), далее содержательное. Каждый пункт —
**бинарная атомарная проверка**; для теста/логики **обязателен негативный критерий** («найди вход,
где сломается»), иначе LLM-судья соглашательствует и помечает всё MET.

1. **Атомарность/целостность (первичный gate).** Один логический смысл; не смешаны фикс+фича;
   коммит компилируется и проходит релевантные тесты. Неатомарный/крупный коммит **возвращай ДО**
   содержательного прохода — blocker ревьюабельности.
2. **Логика vs спека/интент.** Behavioral Comparison: сравни фактическое поведение с ожидаемым по
   AC/spec, **не «зелёные тесты»**. Прицельно — границы, error-состояния, явные ограничения
   требования (зазор happy-path ↔ edge-case).
3. **Business-security (OWASP-линза).** High-risk модули: auth/session, input/output, внешние
   интеграции, фильтрация по владельцу. Именно business-logic vulns, которые SAST/линтеры пропускают.
4. **Тихие регрессии / parity.** Скрытые изменения поведения на критических путях
   (auth/API/shared) — характерный класс AI-дефекта, влияет шире diff.
5. **Качество тестов — мутационным мышлением.** Для КАЖДОГО нового/изменённого теста: «какую
   мутацию кода он ловит? какой строкой сломать, чтобы он упал?». Нет ответа → тест вакуумный
   (**blocker**). Coverage не доверять. Градация **«altitude gap»** (между «вакуумный» и
   «полноценный»): тест ловит мутацию на одном уровне (unit/сериализатор), но НЕ на уровне, где
   живёт риск (HTTP/интеграция) — это **minor-пробел покрытия** (WARN-нота, не blocker-вакуумность),
   с рекомендацией теста нужной высоты.
6. **Производительность.** N+1-запросы (жадная загрузка через `with()`/`load()` не использована —
   Eloquent тянет связанные ингредиенты/шаги рецепта отдельным запросом на каждую строку листинга),
   запросы к БД в цикле, отсутствие индексов или пагинации на объёмных выборках (список рецептов без
   `paginate()`), тяжёлая работа (генерация изображений, импорт, рассылка) прямо в HTTP-цикле вместо
   вынесения в очередь (`queue`/job) — гейты не видят.
7. **Over-engineering.** Не реализовано ли «то, что *может* понадобиться»; сложность не выше
   необходимой.
8. **Чужая среда (обязательный негативный вопрос).** Локальные гейты доказывают код только в
   локальной среде; для каждого коммита спроси: «что случится там, где это НЕ запускалось?»
   Минимум три сценария: **CI-раннер** (пайплайн-файлы исполняются на чужом раннере — версии
   тулов, отсутствие локальных дефолтов; workflow, который ни разу не гоняли, считать
   непроверенным кодом); **prod-установка** (`composer install --no-dev` + `package:discover`/
   `optimize`: dev-пакет, на который безусловно ссылается прод-код/провайдер — фатал);
   **чистая машина** (README/setup с нуля: незакоммиченные пререквизиты, неявные глобальные
   тулы). Прецеденты: cbook `74fe7ab` (CI красный: action-setup без версии pnpm), `fd0e5fe`
   (прод-фатал: провайдер dev-пакета в `bootstrap/providers.php`).

**Формат каждой находки — Evidence-based:** `file:line` + конкретная улика/контрпример («на входе X
вернёт Y вместо Z»), НЕ вердикт «выглядит ок».

### 3.1 Тривиальный коммит (`trivial-scope`, сокращённый проход)

Doc-only коммиты и чистая косметика **без изменения поведения** проходят сокращённую рубрику:
атомарность + подтверждение отсутствия изменения поведения + чистота. В вердикте — явная пометка
**`trivial-scope`** (аудируемо, что проход был сокращённым). **Классификацию «тривиальный/нет**
делаешь ТЫ (ревьюер), не автор. При **малейшем** сомнении в «не меняет поведение» — полная рубрика.

### 3.2 Что НЕ проверять (не дублировать существующее)

- **Минимальный набор гейтов (тесты/typecheck/lint) прогоняешь сам** — нет отдельного
  quality-скрипта, чей зелёный статус можно было бы принять на веру; конкретный тулчейн —
  `./stack-specifics.md`, серилизация тяжёлых прогонов — `./scripts/gate.sh`.
- **НЕ перезапускай полные сьюты** — это зона H.6 (полный гейт интеграционной ветки после батча) и
  Части D. Ты работаешь на уровне ОДНОГО коммита/diff, не композиции.
- **НЕ подменяй** тройную проверку spec (Шаг 5 — ревью дизайна ДО кода), «ревью чистоты» (Шаг 12 —
  следы системы, отдельный агент без `ai/`, режим секретности), приёмку инициативы (Часть D). След
  системы, если **попутно** увидел, помечай как Blocking, но не гоняй второй grep — **ссылайся** на
  Шаг 12.

## 4. Анти-соглашательство и вердикт

- **Негативные критерии обязательны** (§3): «найди вход, где сломается», «докажи, что тест НЕ
  вакуумный».
- **Адверсариальный проход** «попробуй ОПРОВЕРГНУТЬ корректность» — несущая линза (наследует
  [`./briefs/sidecar-verifier.md`](./briefs/sidecar-verifier.md)).
- **Блокируй ТОЛЬКО по подтверждённой Evidence.** Каждая blocker/FAIL-находка ОБЯЗАНА нести
  конкретный контрпример/путь/строку. Без Evidence находка **не может быть блокирующей** (падает до
  WARN) — это снимает поток ложных блокировок (over-correction).
- **Fan-out на high-stakes.** Для `аутентификация/сессии (Laravel auth), файловое хранилище (S3/MinIO), доступ к БД (Eloquent + репозиторный слой), Filament-панель (политики доступа)` (например auth/session/денежных/чувствительных
  данных/миграций) — на каждую blocker-находку порождай **отдельный verifier-субагент**, который
  подтверждает дефект в коде до предъявления; неподтверждённые отсекаются. Для остального достаточно
  самоперепроверки с Evidence.

### 4.1 Формат вердикта (расширенный sidecar-контракт)

База — контракт [`./adr-execution.md`](./adr-execution.md) Часть C /
[`./briefs/sidecar-verifier.md`](./briefs/sidecar-verifier.md). Расширяем (severity в notes,
обязательная Evidence в blocking-находках, `fix-forward-FEAT-NNN` как значение), **сохраняя
парсируемость** — Verdict в **первых 5 строках**, имена полей канона неизменны:

```
**Verdict:** PASS | WARN | FAIL
**Blocking findings:**
- file:line — нарушение + Evidence (контрпример/путь)
**Non-blocking notes:**
- file:line — предупреждение / рекомендация (severity: minor|nit)
**Evidence:**
- <команды / выводы / что проверил>
**Suggested next:** fix-now | fix-forward-FEAT-NNN | advisory | none
```

Пустой список Blocking при PASS — норма, но покажи в Evidence, ЧТО проверил (PASS не вакуумный).
При `trivial-scope` — пометь это в Evidence.

### 4.2 Маппинг severity → вердикт → эффект на merge

| Severity | Вердикт | Эффект на merge |
|---|---|---|
| blocker / major (баг, security, падающий/вакуумный тест, неатомарность, критический путь) | **FAIL** = veto | **merge ЗАПРЕЩЁН** до фикс-коммита |
| minor (не влияет на корректность/безопасность) | **WARN** | advisory: закрыть или принять с записью |
| nit (формат/имя/стиль) | нота при PASS/WARN | не блокирует; батчить, не заваливать шумом |
| чисто | **PASS** | разрешён |

**Критерий достижимости (reachability).** Подтверждённый дефект на пути, **недостижимом в текущей
конфигурации** (за OFF-by-default флагом, за неактивированной фазой) — **НЕ FAIL, а WARN** +
обязательный fix-forward с адресом (§7). НО: если активация запланирована в **этой же** фиче/фазе —
FAIL как обычно. «Спящий» статус обязан быть **доказан Evidence** (конкретный флаг/конфиг и почему
путь не активен), не предположением.

Твой вердикт `Code-Review` не заменяет минимальный набор гейтов (тесты/typecheck/lint) — тот должен
быть зелёным отдельно, сам по себе прогоняется исполнителем/ревьюером вручную (через `gate.sh`).
Красный любого — merge заблокирован. **FAIL=veto** снимаешь **ТОЛЬКО ты сам** (§7), оркестратор не
переопределяет молча.

## 5. Запись результата

**Порядок записи — фиксированный, два отдельных коммита:** (1) сначала review-файлы через
`scripts/ai-commit.sh` (file-per-object, источник истины); (2) затем строки реестра через
`scripts/edit-shared.sh` (тот сам коммитит под локом). Реестр всегда **вторичен** — гейт покрытия
валиден уже после шага (1).

### 5.1 Review-файл (источник истины)

Пиши **отдельный** файл-вердикт `ai/devlog/commits/<repo>/<short-hash>-review.md` рядом с разбором
ADR-009 `<short-hash>-<slug>.md`, **никогда не трогая файл-разбор автора** (разные роли/авторы).
Копируй [`../devlog/commits/_review-template.md`](../devlog/commits/_review-template.md).
Ключ — **as-authored short-hash** (тот же, что ADR-009 — устойчив к squash/rebase). Коммит
review-файла — в `study-cbook-ai` через `scripts/ai-commit.sh` (это артефакт `study-cbook-ai`, НЕ код
клиента — не `scripts/commit.sh`).

### 5.2 Строка в «Реестре ревью»

Добавь строку в таблицу «Реестр ревью» в
[`../devlog/commits/README.md`](../devlog/commits/README.md) (append-в-конец, чужие строки не
трогать). **ОБЯЗАТЕЛЬНО под локом `scripts/edit-shared.sh`** (`README.md` внесён в его whitelist) —
иначе параллельные ревьюеры теряют строки при одновременной правке. Порядок локов —
`booking → edit-shared → shared-docs` (канон — [`./coordination.md`](./coordination.md)). При смене
вердикта после фикса — **новая строка** на фикс-коммит + отметка закрытия (история статуса —
записями, не правкой чужой ячейки).

> Реестр — **вторичная витрина/индекс** для человека; источник истины гейта покрытия — review-файлы
> (§«непроверенные» в [`../devlog/commits/README.md`](../devlog/commits/README.md)). Гейт
> считается по файлам, не по реестру.

## 6. Фикс-цикл: исправление находок — строго по циклу разработки

Фикс находки — **НЕ ad-hoc «сделал коммит»**, а цикл [`./feature-workflow.md`](./feature-workflow.md)
**соразмерно масштабу**:

- **Мелкий фикс в рамках той же фичи (типовой случай).** Спека-дельта НЕ нужна, если фикс приводит
  код к **уже записанному AC** спеки (пример: ошибка-под-ON при AC «→успех» — AC уже был в спеке);
  если же фикс **меняет/дополняет контракт** — сначала правка спеки (+ keystone-дельта оркестратору,
  [`./adr-execution.md`](./adr-execution.md) G.1), потом код. Обязательно: **тест-first** (red ДО
  фикса → green после, feature-workflow Шаг 7) · минимальный набор гейтов тесты/typecheck/lint (Шаг 8) · целостный
  коммит через `scripts/commit.sh` (Шаг 12) · разбор ADR-009 (Шаг 12 п.2.5) · **живой стенд** (Шаг 8)
  — если находка касалась рантайм-поведения.
- **Крупный фикс** (не умещается в фикс-коммит: новые части, миграции, изменение контракта) →
  полноценная **фикс-фича** (под-номер `FEAT-NNN.a`) по полному feature-workflow с собственной
  спекой; в вердикте — `Suggested next: fix-forward-FEAT-NNN.a` (фикс-фича).

**Цикл замыкается ревью.** Каждый новый фикс-коммит **обязательно** проходит ревью: **узкий скоуп**
— (1) закрыта ли конкретная находка; (2) не сломано ли что-то вокруг (регрессия от фикса) — плюс
**полная рубрика §3 для НОВОГО кода фикса, если он нетривиален**. Свой `<hash>-review.md` + строка
реестра; в **исходном** review-файле — отметка «закрыт фиксом `<hash>`» (журнал закрытия находок).
Вердикт исходного коммита снимает **только сам ревьюер** (§7). Повторять до чистого PASS / явно
принятых WARN — **merge/доставка запрещены раньше**. Узкий скоуп по умолчанию — анти-петля
бесконечного ревью.

**«Тихие» фиксы ЗАПРЕЩЕНЫ.** Фикс-коммит без разбора ADR-009 и без ревью = **непроверенный коммит**
— гейт покрытия (§9: git log ↔ review-файлы) его ловит: фиксы входят в сверку **наравне со всеми**
коммитами ветки.

**Репо-специфика workspace действует БЕЗ исключений** — и для фиксов, и для артефактов ревью
(канон — `CLAUDE.md` §Жёсткие правила + [`./coordination.md`](./coordination.md); здесь только якорь,
не пересказ). Гайд не вводит новых правил работы с репо — существующие действуют и здесь:

- **Клиентские репы** (`cbook` и др.): фикс-коммит ТОЛЬКО через `scripts/commit.sh` (формат
  сообщений команды `<type>: <описание> (conventional commits; type ∈ feat|fix|chore|refactor|docs|test|style|perf|build|ci)`, при включённом режиме секретности — 0 следов
  системы/FEAT); работа только в task-worktree ветки фичи; `git push`/MR/доставка — ТОЛЬКО
  пользователь через `scripts/deliver.sh` (агенту запрещён всегда); `git stash` запрещён.

- **`study-cbook-ai`** (артефакты: review-файлы, разборы, реестры, impl.md): коммит ТОЛЬКО через
  `scripts/ai-commit.sh` (своя зона); общие файлы (README-реестры) — через `scripts/edit-shared.sh`;
  публикация `scripts/ai-push.sh` агенту разрешена.

### 6.1 Шаблон запуска фиксера (копировать в промпт)

```
Ты действуешь по ВСЕМ действующим правилам workspace без исключений: CLAUDE.md (жёсткие правила,
репо-специфика клиентские/study-cbook-ai), guides/feature-workflow.md (цикл разработки),
guides/coordination.md (параллельность, локи) — ревью и фикс НЕ исключение из процесса, а его часть.

Ты — исполнитель фикса находок ревью: FEAT-NNN · ветка feat/<slug> · worktree tasks/<slug>.
Находки — в ai/devlog/commits/<repo>/<short-hash>-review.md (Blocking findings + notes).
Фикс — строго по фикс-циклу ai/guides/commit-review.md §6: масштаб (мелкий в той же фиче /
фикс-фича FEAT-NNN.a); контракт меняется → сначала спека (+keystone-дельта); тест-first (red ДО
фикса → green после) · минимальный набор гейтов (тесты/typecheck/lint) · коммит commit.sh · разбор ADR-009 · живой стенд при
рантайм-находке. «Тихий» фикс запрещён. После фикса сигналь «ready к ревью» — вердикт исходного
коммита снимает ТОЛЬКО исходный ревьюер, не ты.
```

## 7. Политика находок и эскалация (минимизация техдолга)

- **FAIL / blocker** → **фикс-коммит исполнителем ДО merge** (gate-модель fix-before-merge). Фикс —
  строго по фикс-циклу §6 (тест-first, гейты, разбор, обязательное ревью фикса). Merge запрещён,
  пока blocker не закрыт.
- **WARN / minor** → advisory: либо закрывается фикс-коммитом, либо **явно принимается
  оркестратором с записью** (журнал закрытия в review-файле + отметка в реестре). Молча не
  игнорируется.
- **nit** → не блокирует; батчить в одну ремарку; повторяющиеся — в линтер/чеклист.
- **Снятие FAIL-veto — ТОЛЬКО сам ревьюер:** повторным ревью после фикс-коммита (§6) либо после
  предъявления **контр-Evidence** (новый довод, не «пуш-бэк» автора). Оркестратор **НЕ вправе молча
  переопределить** вердикт. Неразрешимое несогласие ревьюера и оркестратора/исполнителя →
  **эскалация владельцу (`Dmitriy`)** с фиксацией позиций и решения в review-файле.
- **fix-forward допустим ТОЛЬКО с задокументированным адресом** (`FEAT/фаза` + строка в журнале
  ADR); недокументированный хак/kludge = блок. `Suggested next: fix-forward-FEAT-NNN`, где `NNN`
  может быть и **текущей фичей** (фикс-коммит в той же ветке до доставки) — это **предпочтительный
  адрес** по минимизации техдолга; будущий FEAT — только если фикс требует ещё не существующих
  частей.
- **Анти-паттерн бесконечных переделок.** Планка одобрения — Google «изменение определённо улучшает
  здоровье кодовой базы», не совершенство. Ты не «сдаёшься» при возражении автора без нового довода,
  но и не гоняешь косметические циклы: nit не блокирует, WARN закрывается/принимается — ветка не
  застревает.

## 8. Соло-режим (явно)

Соло-исполнитель играет обе роли поочерёдно: коммитит и пишет разбор ADR-009 как **автор** → затем
**порождает субагент-ревьюера** (чистый контекст, `Opus 4.8`) на свои коммиты по этому
гайду → отрабатывает находки фикс-коммитами → только потом сигналит пользователю «готово к
доставке». «Ревьюер ≠ автор» держится за счёт **отдельного субагента**, не смены шляпы в одном
контексте.

## 9. Чек-лист оркестратора перед merge (покрытие ревью)

Перед merge (вход B.2 / переинвентаризация H.2) оркестратор сверяет **git log ↔ review-файлы**:

```
□ Для КАЖДОГО коммита git log <base>..<branch> существует
  ai/devlog/commits/<repo>/<short-hash>-review.md
□ Вердикт каждого — PASS или WARN (не FAIL с незакрытым blocker)
□ Все blocker закрыты фикс-коммитами (в review-файле — отметка «закрыт фиксом <hash>»,
  фикс-коммит сам имеет review-файл §6)
□ WARN — закрыты фиксом ИЛИ явно приняты с записью в журнале review-файла
```

**Формула «непроверенных» (единый носитель — здесь, §9).** Коммит считается **непроверенным**,
если для его **as-authored short-hash** в `git log <base>..<branch>` НЕ существует
`ai/devlog/commits/<repo>/<short-hash>-review.md` с вердиктом PASS/WARN, ЛИБО существует review-файл
с вердиктом FAIL и незакрытым blocker'ом. Непроверенный коммит → **merge не проводится**, вернуть на
доработку. Реестр ревью в [`../devlog/commits/README.md`](../devlog/commits/README.md) (§Реестр ревью)
— **вторичная витрина**, формулу не дублирует, а ссылается сюда.

## 10. Пример (короткий; замените под свой стек)

Коммит `abc1234` (`fix: ограничить редактирование рецепта его автором`, фильтр по владельцу),
фича FEAT-030:

- прочитал spec (AC: «редактировать рецепт может только его автор»), keystone, разбор ADR-009,
  `git show abc1234`;
- рубрика §3: нашёл — `RecipeController@update:42` вызывает `$recipe->update(...)` без
  `$this->authorize('update', $recipe)` — политика `RecipePolicy::update` существует, но нигде не
  вызывается → на входе «пользователь Б шлёт `PATCH /recipes/{id}` с id чужого рецепта пользователя
  А, своим токеном» контроллер примет и сохранит правку чужого рецепта (Evidence: путь запроса,
  метод контроллера);
- тест `RecipeUpdateTest::test_update` проверяет только happy-path автора рецепта — **вакуумен** к
  этому классу дефекта: убрать `authorize()` из кода — тест всё равно зелёный;
- вердикт **FAIL**, blocking: `RecipeController.php:42` (нет проверки владельца) +
  `RecipeUpdateTest.php:18` (тест не ловит мутацию — нет негативного кейса «чужой пользователь»);
  `Suggested next: fix-now`;
- записал `cbook/abc1234-review.md` (коммит `scripts/ai-commit.sh`), затем строку в реестр под
  `scripts/edit-shared.sh` (порядок §5);
- исполнитель дал фикс-коммит `def5678`: добавил `$this->authorize('update', $recipe)` в
  контроллер + Pest-тест `test_forbids_updating_foreign_recipe` (чужой пользователь → 403) — сначала
  красный (до authorize) → зелёный после; узкое ревью §6 → PASS → отметка «закрыт фиксом def5678» в
  `abc1234-review.md` + новая строка реестра.
