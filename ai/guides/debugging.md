# Debugging — поиск причины бага (root-cause playbook)

> **Аудитория:** AI-ассистент и разработчик проекта.
> **Когда сюда:** тест упал · «данные не те» · рендер пуст · внешняя интеграция молчит/врёт. Ты ищешь **ПРИЧИНУ** уже случившегося бага.
> **Когда НЕ сюда:** если задача — ПРОВЕРИТЬ поведение живьём (выбрать слой теста, прогнать сценарий) → [`./live-acceptance.md`](./live-acceptance.md). Если пишешь новую фичу → [`./feature-workflow.md`](./feature-workflow.md).

> ⛔ **Гигиена клиентского репозитория** (см. `../architecture.md` §8): отладочные `print`/логи — только с маркером `~wip~`, ВСЕ убрать до готовности; в логах нет секретов/чувствительных данных.

---

## 0. Главные правила (нарушение = потерянные часы)

1. **Сначала воспроизведи, потом чини.** Пока баг не воспроизводится стабильно — ты не отлаживаешь, а гадаешь. Первый артефакт дебага — **минимальный повторяемый repro** (команда / тест / сценарий), а не гипотеза.
2. **Фикс — только по доказанной причине, не по симптому.** «Похоже, помогло» ≠ причина. Ты должен уметь сказать: «значение разошлось с ожиданием ВОТ ЗДЕСЬ, потому что ВОТ ЭТО».
3. **На каждый пофикшенный баг — регрессионный тест.** Тест обязан быть **КРАСНЫМ до фикса** и зелёным после. Красный-до доказывает, что тест реально ловит класс, а не проходит вакуумно.
4. **Не меняй код и тест одновременно, не поняв причину.** Если правишь и то и другое «наугад» — теряешь единственную точку опоры (что именно поменяло поведение).

## 1. Классификация симптома → с чего начать

Определи класс симптома — он задаёт первый слой, куда смотреть.

| Симптом | Вероятный слой | Первый шаг |
|---|---|---|
| **Тест упал** (был зелёный / новый красный) | зависит — сначала пойми, врёт тест или код | Прочитать assertion: что ожидалось vs получено. Проверить `known-flakes` (§4) |
| **Данные не те** (пусто / меньше строк / чужие / stale) | хранение / выборка / фильтр | Снять реальное значение из хранилища на границе чтения |
| **Рендер пуст** (виден каркас, нет контента) | выход: сериализация/парсинг/маппинг на стыке вход→UI | Воспроизвести БЕЗ UI (данные на входе рендера) |
| **Внешняя интеграция** (API молчит/ошибка/не тот ответ) | граница с внешним миром | Залогировать реальный запрос+ответ на границе; проверить контракт |

**Базовая идея:** одно действие проходит цепочку **вход → обработка → хранение → выход**, и баги почти всегда живут **на границах между слоями** — часто **тихо**, без ошибки (значение молча деградировало в fallback, фильтр молча срезал строки, парсинг молча вернул пустоту).

## 2. Алгоритм (бинарный поиск по слоям)

Идёшь сверху вниз; каждый шаг **отсекает половину системы**.

**Шаг 1 — Воспроизведи минимально.**
Сведи баг к самому дешёвому повторяемому виду: один тест / одна команда / один сценарий с фиксированным входом. Если удаётся воспроизвести **без UI/сети** (на чистых данных) — половина системы уже исключена. Repro должен быть детерминированным: тот же вход → тот же баг.

**Шаг 2 — Раздели систему на слои и найди границу.**
Разложи путь на стыки: `вход → обработка → хранение → выход`. Проверяй значение **на каждой границе** и ищи **первую границу, где значение разошлось** с ожиданием:

```
вход (что реально пришло?)
  → обработка (что на выходе бизнес-логики?)
  → хранение (что реально записалось / прочиталось?)
  → выход (что ушло в UI/ответ?)
```

Бинарь: проверь середину цепочки. Если там значение уже неверное — баг **выше** (вход/обработка). Если верное — баг **ниже** (хранение/выход). Повтори на половине. Обычно 2–3 замера локализуют границу.

**Шаг 3 — Назови расхождение точно.**
На подозрительной границе сравни фактическое значение с **контрактом** (тип / схема / ожидаемая форма). Формулируй машинно: «пришло `{a, b}`, ожидалось `{a, c}`»; «фильтр вернул 3 строки из 10, срезала политика X»; «внешний API вернул 200 с пустым `items`, а не 404». Это превращает «гадание по слоям» в **названную границу + названное расхождение** — а это и есть причина.

**Шаг 4 — Регрессионный тест на РЕАЛЬНОЙ форме (red→green).**
Напиши тест, который гоняет **реальное** значение с границы (не выдуманное руками — hand-shaped данные часто «зелёные», как раз пропуская баг). Убедись, что он **КРАСНЫЙ** до фикса. Затем чини, пока не зелёный.

**Шаг 5 — Фикс + верификация.**
Устрани **причину** на найденной границе (не замазывай симптом «ещё дальше по цепочке»). Прогони гейты проекта:

```bash
# ADAPT: команды тестов/typecheck по слоям — см. stack-specifics.md §Команды (гейты)
./vendor/bin/sail artisan test
./vendor/bin/sail bin phpstan analyse
```

Баг закрыт, когда: repro больше не повторяется, регресс-тест зелёный, весь набор зелёный.

**Шаг 6 — Запиши баг в devlog с тегом класса.**
Класс бага фиксируется тегом (для grep-индексируемости «а где мы уже наступали на это»). Каталог тегов и формат — единый источник в [`../devlog/README.md`](../devlog/README.md) §Каталог тегов (`security-leak`, `validation-missing`, `concurrency-race`, `regression-test-missing` и т.д.). Баг с фиксом → строка в `impl.md` фичи (или в `devlog/YYYY-MM-DD.md`, если это trivial-fix) + тег в YAML frontmatter.

## 3. Анти-паттерны ⛔

### Чинить наугад
```
❌ «Поменяю тут, вдруг поможет» → помогло → едем дальше
✅ Сначала докажи причину (границу + расхождение), потом фикс
```
Случайный фикс без понятой причины = баг вернётся (или уже мутировал в другой).

### Глушить тест
```
❌ skip / комментарий / ослабить assertion, чтобы «стало зелено»
✅ Красный тест = сигнал. Либо код неверен, либо тест неверен — разберись, что именно
```

### Менять код и тест одновременно вслепую
```
❌ Правлю реализацию И assertion в одном заходе, не поняв, кто из них врал
✅ Зафиксируй одну сторону как опору. Сначала пойми, где истина, потом правь другую
```

### Фикс по симптому, не по причине
```
❌ Рендер пуст → подставлю заглушку в UI, чтоб не было пусто
✅ Найди, ГДЕ данные потерялись (обычно выше по цепочке), и почини там
```

### Тест на выдуманных данных
```
❌ Регресс-тест на hand-shaped объекте → зелёный и до фикса (вакуумный)
✅ Тест на РЕАЛЬНОЙ форме значения с границы → красный до фикса
```

### Фикс без регресс-теста
```
❌ Починил, пошёл дальше — тег regression-test-missing
✅ Каждый баг оставляет тест, который бы его поймал
```

## 4. Известные флейки — сверься ПРЕЖДЕ диагностики

Если тест падает недетерминированно (то красный, то зелёный) — **не диагностируй с нуля**, сначала проверь реестр известных флейков `../process-metrics/known-flakes.md` (если в проекте включён модуль Process Retro — см. [`./process-retro.md`](./process-retro.md)). Тест в реестре со статусом `активен` → повтори прогон / отметь, НЕ трать диагностику. Теста нет в реестре → диагностируй и **внеси** его, чтобы следующий не переплатил.

Если реестра в проекте ещё нет — это сигнал, что после N-го повтора одного флейка стоит его завести.

## 5. Инструменты дебага проекта

> `# ADAPT:` этот раздел параметризуется под стек — полный набор в [`./stack-specifics.md`](./stack-specifics.md) (`Laravel Telescope, ray()/dd(), sail artisan tinker, Laravel Pail (логи), Vue Devtools, Vite HMR`). Ниже — универсальные приёмы; конкретные команды подставь при развёртывании.

- **Логи стенда:** где лежат логи бэкенда/фронта/воркеров (nohup-файлы или foreground stdout); на прод-хостах — журнал сервиса (зона оператора). `# ADAPT: → stack-specifics §DEBUG_TOOLS`.
- **Отладчик / REPL:** точечный `breakpoint()`/`pdb` (или аналог стека); одноразовый прогон через shell/management-команду с фиксированным входом.
- **Снять значение на границе:** временный `~wip~`-лог на стыке (вход/выход сериализатора, выборка до/после фильтра); проверь **реальную форму** данных, пересекающих провод.
- **Хранилище:** прямой запрос **под реальной ролью/правами, НЕ под суперюзером** — иначе фильтры доступа (изоляция чувствительных данных) не сработают и баг «данные пропали»/«чужие данные» не воспроизведётся. Если у проекта несколько БД/контуров — читаешь ли ты из нужного? `# ADAPT: → stack-specifics §Инварианты (несколько БД/роутер)`.
- **Внешние интеграции:** записать реальный HTTP запрос+ответ (маскируя секреты/ПДн); прогнать контракт против **реального** ответа, не против моков.
- **Рендер пуст:** воспроизведи БЕЗ UI — проверь ответ API (curl) на реальную форму (маппинг на границе, напр. snake↔camel — частый «тихий» класс).

> ⛔ Временные `print`/логи и любые отладочные пометки — с маркером `~wip~`; ВСЕ убрать до готовности (§8 гигиена). В логи не выводить токены/пароли/чувствительные данные.
