
# Process Retro — ретро процесса разработки (ОПЦИОНАЛЬНЫЙ уровень зрелости)

> **Аудитория:** AI-ассистент в роли оркестратора крупных инициатив.
> **Статус: ОПЦИОНАЛЬНЫЙ модуль M7.** Включай, **только когда** в проекте пошли многофичные инициативы через [`./adr-execution.md`](./adr-execution.md) (оркестратор + субагенты). Для одиночных фич и малых проектов этот модуль — оверхед: **не заводи его наперёд**. При OFF: этот файл и каталог `../process-metrics/` удаляются, а в `../memory.md` остаётся строка «включить при первой крупной инициативе».

---

## Зачем этот модуль

Когда крупная инициатива катится десятками фич через субагентов, у **самоанализа процесса нет durable-субстрата**: замеры (сколько стоила фича, где ловились дефекты, сколько было петель red→green) добываются ad-hoc и **теряются** к следующей инициативе. Каждое ретро либо выводит данные заново, либо не проводится вовсе.

Process Retro закрывает это: **дешёвый ручной ритуал** ретро при закрытии инициативы + **опциональный машинный леджер метрик**, из которого ритуал берёт числа. Это НЕ рантайм-надзор над агентами и НЕ enforcement — это дисциплина самоанализа.

> **Что это НЕ:** не автоматический supervisor субагентов, не жёсткий токен-бюджет, не автопереписывание гайдов. Ретро **предлагает** улучшения — материализует их человек/оркестратор через хартию (§в).

## (а) Ритуал ретро при закрытии инициативы

Ретро-пасс — **гейт закрытия** инициативы: инициатива не закрыта, пока ретро не проведён и ретро-запись не создана. Что смотреть (срезы самоанализа):

| Срез | Вопрос | Сигнал-кандидат |
|---|---|---|
| **1. Где ловились дефекты** | На какой стадии поймана каждая blocking-находка: спека / тесты / гейты / живая приёмка / **после merge**? | Чем позже стадия, тем дороже. Escaped-дефекты (после merge) — самый дорогой класс, отдельный фокус |
| **2. Петли и трение** | Сколько было циклов red→green? Merge-конфликтов? Фальстартов («готово», а не готово)? Повторных заходов? | Повторяющееся трение = кандидат в улучшение процесса |
| **3. Экономика субагентов** | Сколько «стоила» каждая роль (impl / spec / verifier / orchestrator)? Где рычаг экономии? | Систематический перерасход на одном классе работы = кандидат |
| **4. Калибровка выбора моделей** | Как часто модель субагента приходилось переквалифицировать (взяли дешёвую, а нужна сильная, или наоборот)? | Систематическая недо-/переквалификация = кандидат в уточнение правил выбора модели |
| **5. Дисциплина канонов** | Сколько раз нарушен канон процесса (пропущен шаг, обойдён гейт)? | Каждое нарушение = кандидат в прицельный guard либо обоснованный отказ |

Ретро можно провести **качественно** (просто пройтись по срезам глазами) — или, если ведётся леджер (§б), опереться на машинный снимок метрик.

## (б) Опциональный машинный леджер метрик

> **Обновление владельца 2026-08-03:** «опциональность» ниже — снята: решением владельца метрик-леджер **обязателен начиная со СЛЕДУЮЩЕЙ инициативы** (до сих пор был опционален). Основание — первое ретро [`../process-metrics/retro-recipe-domain.md`](../process-metrics/retro-recipe-domain.md): срезы «экономика субагентов» и «калибровка выбора моделей» дали **WARN «не измерено»** именно из-за отсутствия замеров. DoD закрытия фичи дополнен ([`./feature-workflow.md`](./feature-workflow.md) Шаг 10), полнота леджера — `scripts/ledger-check.sh`.

Durable-субстрат замеров. Если решил вести — формат: **JSONL, одна строка на фичу, один файл на инициативу** (`../process-metrics/adr-NNN.jsonl`).

> **Почему JSONL, а не md-таблица:** параллельные субагенты дописывают **свои** строки в конец (append-only) — нулевой merge-конфликт. Md-таблица конфликтовала бы на каждом параллельном append (а merge-конфликты — сама одна из метрик, которую мы меряем). Плюс машиночитаемость: построчный `JSON.parse` для агрегатора.

**Append-only:** строки не переписываются и не удаляются. Исправление — новая correction-строка + пояснение в `notes`.

### Схема строки

| поле | тип | смысл |
|---|---|---|
| `feat` | string | `FEAT-NNN` фичи (ключ полноты); для cross-feature ролей — sentinel вида `adr-NNN/spec-pass` |
| `adr` | string | номер инициативы |
| `role` | enum | `impl \| spec \| verifier \| orchestrator` — какая роль отработала |
| `model` | enum | класс модели, что выполнял (адаптируй набор под свои роли-модели) |
| `tokens` | number\|null | из сводки субагента; `null` — недоступно (толерантно) |
| `red_green_loops` | number | сколько было петель red→green |
| `merge_conflicts` | number | merge-конфликты при интеграции фичи |
| `defect_catch_stage` | enum\|null | стадия поимки blocking-находки: `spec \| tests \| gate \| acceptance \| post-merge` |
| `canon_violations` | number | счётчик нарушений канона; каждое `>0` — кандидат в guard |
| `notes` | string | свободный текст (пояснения, ссылки, исправления) |

**Толерантность к пропускам:** обязателен только **ключ** `feat`/`adr`/`role`/`model`; числовые поля могут быть `null`, если сводка их не дала. Цель — «фиксировать что доступно», а не блокировать по неполноте. `null` у `defect_catch_stage` = «не оценивалось», а НЕ «дефектов не поймано» (последнее лучше явно сказать в `notes`).

**Кто пишет строку:** обычно **оркестратор** — usage-числа (`tokens`) видны только ему в момент завершения субагента; сам субагент своего usage не знает. Субагент возвращает то, что знает (role/model/петли/стадия/нарушения), оркестратор дописывает строку с usage.

Полный формат, схема и примеры — в [`../process-metrics/README.md`](../process-metrics/README.md).

### Чекер полноты леджера (опционально, warn-only)

Чтобы леджер не оказался с дырами к моменту ретро — заведи **чекер полноты**: на каждую **закрытую** (`✅`/`⚠️`) фичу таблицы инициативы должна существовать строка в леджере с обязательными **ключами**. Ключевые свойства чекера:

- **Проверяет наличие КЛЮЧА, не значения.** `null`-значение — ОК (ядро толерантности к пропускам): warn только на **отсутствие** ключа.
- **Warn-only, не блокирует CI/DoD.** Пропуск строки не валит сборку — он **усиливает следующий ретро сигналом** «тут метрику потеряли». Опциональный `--strict` — только для локального прогона.
- **Считает только закрытые фичи.** `⬜`/`🚧` игнорируются; пустой список закрытых → тихий проход (анти-self-lock: чекер не падает на только что заведённой инициативе).

Это дешёвая durable-дисциплина: она не заставляет вести метрики, но не даёт молча потерять их к ретро.

## (в) Хартия ретро-решений

Правила, по которым кандидат ретро **становится (или НЕ становится)** изменением. Хартия защищает канон от церемониальных и опасных правок:

- **Менять канон только при измеренном классе (≥2–3 инцидента/замера).** Один случай → не канон, а заметка.
- **Ничего не ослаблять.** Ретро может только ужесточить / уточнить / удешевить. Упрощение ≠ снятие гейта. Снятие гейта — отдельное решение владельца, не диспозиция ретро.
- **Non-vacuous.** Любой новый guard/тест из ретро ловит реальный класс: red ДО → green после. Вакуумных правил не вводим.
- **Single-source.** Изменение процесса — правкой существующего канона (гайд / ADR), не новым параллельным документом.

### Градация риска

| Класс правки | Как проводить |
|---|---|
| **Доки / пояснения** (уточнить формулировку, добавить пример) | **Применить сразу** (правка + запись в ретро) |
| **Процессный канон** (новый гейт / шаг / guard процесса) | Через **мини-ADR** (обосновать измеренным классом) |
| **Всё около безопасности / денег / прод-данных / внешних систем** | Мини-ADR **+ решение владельца** (`Dmitriy` санкционирует до исполнения) |

**Тайбрейкер: сомневаешься «док-фикс или процессный канон» → бери мини-ADR.** De-facto смена поведения процесса под видом «уточнения формулировки» запрещена.

## (г) Реестр известных флейков

Ведёшь ретро — веди и `../process-metrics/known-flakes.md`: durable-реестр недетерминированных тестов. Дисциплина: **сверься с реестром ПРЕЖДЕ, чем диагностировать «новый» падёж теста.**

- Тест в реестре (`активен`) → повтори прогон / отметь, НЕ диагностируй с нуля.
- Теста нет в реестре, но он флейкует → диагностируй и **внеси** его строкой — следующий исполнитель не переплатит.
- `починен` — историческая запись (не удаляется, чтобы повторный регресс узнавался, а не переоткрывался с нуля).

Реестр — **не enforcement** (не блокирует CI), а дешёвая durable-память. Формат — в [`../process-metrics/known-flakes.md`](../process-metrics/known-flakes.md).

## (д) Выход ретро

Итог ретро-пасса — короткая **ретро-запись** рядом с леджером (`../process-metrics/retro-<инициатива>.md`, по шаблону [`../process-metrics/retro-TEMPLATE.md`](../process-metrics/retro-TEMPLATE.md)):

- **снимок-сводка** (метрики из леджера, если он есть; иначе — качественная оценка по срезам);
- **срез-вердикты** по каждому срезу самоанализа (§а);
- **список кандидатов-улучшений с диспозицией**: `принято (применено сразу) / открыт мини-ADR / отложено / отклонён (< порога)`.

Пустой список кандидатов допустим — но тогда явно зафиксируй причину («данных нет» / «ни по одному классу порог ≥2–3 не выполнен»), чтобы ретро не превратилось в формальную отписку.

## Быстрый чеклист ретро-пасса

```
[ ] Инициатива закрывается → ретро-пасс проведён (гейт закрытия)
[ ] Пройдены 5 срезов самоанализа (§а)
[ ] Чекер полноты леджера прогнан (если ведётся леджер) — дыры замечены ДО снимка
[ ] Снимок метрик снят (если ведётся леджер) ИЛИ качественная оценка
[ ] Кандидаты выписаны, каждому — диспозиция по хартии (§в)
[ ] Каждый кандидат градуирован по риску (док / мини-ADR / +владелец)
[ ] Ретро-запись создана (retro-<инициатива>.md)
[ ] Реестр флейков актуализирован, если ловились флейки
```
