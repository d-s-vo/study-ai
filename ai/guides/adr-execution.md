# Гайд: Исполнение ADR-инициативы (оркестратор + субагенты, живой документ)

> 🛑 **STOP — это гайд для КРУПНОЙ инициативы из десятков фич** (оркестратор + субагенты, живой документ ADR).
> Если у тебя **ОДНА фича**, которой нужен **один ADR-решение** (архитектурный выбор) — тебе **НЕ сюда**:
> вернись в [`./feature-workflow.md`](./feature-workflow.md) **§4.5 «ADR-решение»**. Один decision-ADR (`adr/NNN`) ≠ ADR-инициатива.

> **Аудитория:** AI-ассистент в роли **оркестратора** крупного блока функционала (внутри — бриф для **субагентов-исполнителей**).
> **Это слой НАД [`./feature-workflow.md`](./feature-workflow.md).** `feature-workflow.md` отвечает на вопрос «как сделать **одну** фичу». Этот гайд отвечает на вопрос «как провести **целую ADR-инициативу** из десятков фич: последовательно, качественно, без переполнения контекста — делегируя каждую фичу субагенту и поддерживая ADR как **живой документ**».
> **Ссылки:** [`./feature-workflow.md`](./feature-workflow.md) — алгоритм одной фичи · `../adr/` — где живут инициативы · `../architecture.md` — архитектура и инварианты · `../devlog/features/` — артефакты фич (spec/impl/retro).

> **Части (в порядке следования; буквы стабильны — на них ссылаются другие файлы):** A контракт ADR · B работа оркестратора (B.1–B.5) · C бриф субагенту · G specs-first гейт фазы · H merge-дисциплина (9 уроков) · E роли/брифы · F ротация/handoff · D финальная приёмка.

> ⛔ **Гигиена клиентского репозитория (действует на всю инициативу).** Клиентские репы (`cbook`, `(отсутствует)`, ...) не несут следов системы — полное правило `../architecture.md` §8. Оркестратор ОБЯЗАН прошить это в бриф КАЖДОГО субагента: ноль упоминаний системы/FEAT/агентов/спеков в коде/комментариях/коммитах/ветках; ветки `feat/<slug>` **без номеров** (маппинг FEAT-NNN ↔ ветка — `../devlog/features/README.md`); временные пометки только `~wip~` (все убрать до готовности); коммит только `scripts/commit.sh`; `git push`/MR — **только пользователь**. Финальная приёмка (Часть D) включает **«ревью чистоты»** свежим субагентом без доступа к `ai/`.

## Зачем этот гайд

Крупный функционал реализуется по проверенной схеме:

```
1. Расписать инициативу в ADR        (решение «почему» + дизайн)
2. Спланировать список фич           (декомпозиция → таблица фаз и фич)
3. Написать спеки                    (specs-first по фазе)
4. Запустить ОРКЕСТРАТОРА            (идёт по таблице, на каждую фичу — субагент)
        ↳ субагент реализует по feature-workflow.md
        ↳ субагент актуализирует ADR как ЖИВОЙ ДОКУМЕНТ
```

Раньше **весь этот алгоритм** копировался в каждый ADR. Это дублирование: ~200 строк процедуры в каждом новом ADR, рассинхрон между копиями, шум.

**Этот гайд — единственный канонический источник алгоритма.** Новый ADR его **не переписывает**, а **ссылается**:
> «Исполнение — строго по `guides/adr-execution.md` (оркестратор + субагенты, живой документ).»

ADR остаётся носителем только **данных своей инициативы**: таблица фич, журнал, keystone-контракты, ADR-специфичные инварианты. **Алгоритм** живёт здесь.

## Терминология и роли

| Термин | Что это |
|--------|---------|
| **ADR-инициатива** | Крупный блок функционала, расписанный в `adr/NNN-*.md`, с разделом «План реализации» (таблица фаз/фич + журнал) |
| **Оркестратор** | Основной поток ассистента. **НЕ реализует фичи сам** — ведёт таблицу, делегирует, принимает сводки, держит общую картину. Его контекст должен оставаться **узким** |
| **Субагент-исполнитель** | Запускается оркестратором (Agent-tool) на **ОДНУ** фичу. Проходит весь `feature-workflow.md` в **своём** контексте, актуализирует живой ADR, возвращает **сжатую сводку** |
| **Spec-субагент** | Запускается на **всю фазу** (не на одну фичу): пишет `spec.md` всех её фич + заполняет keystone-секцию ADR **до** реализации. Держит картину фазы целиком (имплементационный субагент — нет). См. Часть G |
| **Вложенный агент** | Субагент-исполнитель может сам запускать агентов (разведка/адверсариальная проверка/фан-аут XL) — инструмент качества, не обязанность |
| **Живой документ** | ADR, который **обновляется после каждой фичи** (статус в таблице + строка в журнале + правки keystone-контрактов). Главный канал передачи знания между субагентами |
| **Keystone-дельта** | Изменение keystone-контракта, которое субагент возвращает оркестратору **ТЕКСТОМ** (не правит ADR сам при параллельной работе). Оркестратор вносит дельты в ADR **серийно** — см. Часть G.1 |

> **Почему именно «оркестратор + субагенты», а не «всё в одном потоке».** Инициатива из ~10–30 фич не помещается в один контекст: чтения файлов, правки, прогоны тестов на каждую фичу его переполняют. Субагент работает в **своём** окне → не раздувает контекст оркестратора. Это **замена ручного `/compact`**. **Канал передачи знания между субагентами** — durable-файлы (`memory.md` + журнал ADR + `impl.md`), а **не** контекст оркестратора: каждый субагент в шаге 1 их читает и восстанавливает картину.

> **Экономия контекста оркестратора — что делегировать ⚠️** Оркестратор **код фич НЕ пишет** — держит у себя только выводы. Делегируй всё «шумное»: **каждую фичу** → субагенту-исполнителю; **широкую разведку/поиск по многим файлам** → read-only Explore-агенту (тебе нужен вывод, не дампы файлов); **ревью / перепроверку / живую приёмку** → отдельному агенту-скептику; **независимые куски** → параллельным агентам одним сообщением. Субагент возвращает **сжатую сводку** (B.5) — её и держи в контексте, не сырой ход работы. Мелкие правки в 1–2 файла оркестратор делает сам — субагент тут лишний оверхед.

> **Глубина оркестрации ≤ 3 уровня.** `оркестратор → субагент-исполнитель → его вложенные разведчики/ревьюеры` — и не глубже. Вложенный агент **не** запускает суб-суб-агентов на новую самостоятельную работу: теряется трассируемость, раздувается стоимость, размывается ответственность. Нужна ещё одна фича — верни её оркестратору как сигнал пере-декомпозиции (см. B.3), а не порождай новый уровень.

> **Выбор модели субагента ⚠️** При запуске субагента **явно** указывай модель (не дефолт): рутина (механические правки по брифу, разведка/поиск, прогон гейтов, доки по шаблону) → слабая/дешёвая; сложное (авторинг спеков/ADR, нетривиальная реализация, адверсариальное ревью, дебаг с неизвестной причиной, security, живая приёмка) → сильная. Сомневаешься — сильная. Правило действует и для вложенных агентов. **Имена моделей проекта: рутина → `Sonnet 5`, сложное → `Opus 4.8`, сомневаешься → `Opus 4.8`.**

## Жизненный цикл инициативы (карта)

```
┌─ ФАЗА ПЛАНИРОВАНИЯ (оркестратор лично или spec-субагент) ───────────────────┐
│ 1. ADR написан: контекст, решение, дизайн, инварианты, альтернативы          │
│ 2. Декомпозиция на фичи → таблица фаз и фич (статус-колонка, столбец «Зависит»)│
│ 3. Keystone-контракты + сквозные требования зафиксированы                     │
│ 4. Specs-first для первой фазы: spec.md ВСЕХ её фич + перечитка/валидация (G)│
└──────────────────────────────────────────────────────────────────────────────┘
            │
            ▼
┌─ ФАЗА ИСПОЛНЕНИЯ (АВТОНОМНО, по одной фиче за проход, без клянченья) ────┐
│  loop:                                                                        │
│    выбрать следующую фичу (⬜, все зависимости ✅)                             │
│    если входим в НОВУЮ фазу → сперва specs-first-гейт этой фазы               │
│    делегировать субагенту  ──►  субагент: feature-workflow.md (шаги 1–11)    │
│                                  субагент: актуализировать живой ADR          │
│                                  субагент: вернуть сжатую сводку              │
│    принять сводку → верифицировать живой документ обновлён → следующая фича   │
│  (развилки по ходу решаются как архитектор: целостность + мин. техдолг)        │
└──────────────────────────────────────────────────────────────────────────────┘
            │  все фичи ✅/⚠️
            ▼
┌─ ФИНАЛЬНАЯ ПРИЁМКА (цели ADR выполнены и система РЕАЛЬНО работает) ────────┐
│  субагенты перепроверяют: сверка целей ADR · полный зелёный прогон ·         │
│  реальный браузер / curl / e2e-скрипт · адверсариальные инварианты            │
│  дефект → фикс-фича (feature-workflow) → повторить приёмку. Закрыт DoD → доклад│
└──────────────────────────────────────────────────────────────────────────────┘
```

## Часть A — Что должен содержать ИСПОЛНЯЕМЫЙ ADR (контракт)

Чтобы оркестратор смог вести инициативу, в ADR должен быть раздел **«План реализации»** (номер любой — в одном проекте §X, в другом §Y) со **стандартным набором подразделов**. Это и есть данные, которые ADR несёт сам; алгоритм над ними — этот гайд.

| Подраздел | Роль | Обязателен |
|-----------|------|-----------|
| **Операционный цикл** | **Одна строка-ссылка на этот гайд** (а не копия процедуры) | ✅ |
| **Сквозные требования** | Инварианты-как-AC для **каждой** фичи инициативы (типизация, безопасность, ADR-специфика) | ✅ |
| **Правило живого документа** | Что обновлять после каждой фичи (можно тоже сослаться сюда — см. Часть B) | ✅ |
| **Таблица фаз и фич** | Статус-колонка · FEAT-NNN · имя/пакет · столбец «Зависит» · «что даёт» | ✅ |
| **Критический путь** | Порядок и ветки параллелизма (что от чего зависит) | ✅ |
| **Keystone-контракты** | Field-list ключевых типов/контрактов, от которых зависят ≥3 фичи (specs-first) | ✅ если фазы делят контракты |
| **Журнал реализации** | Пустой до старта; растёт по строке на фичу (канал знания между субагентами) | ✅ |
| Проверка полноты / Out-of-scope | Что из ADR покрыто фичами; что явно вне scope | рекомендуется |

### Минимальный скелет раздела (копировать в новый ADR)

```markdown
## N. План реализации (roadmap фич)

> Исполнение — строго по `guides/adr-execution.md` (оркестратор + субагенты, живой документ).
> Нумерация фич продолжает сквозную (последняя занятая — FEAT-XXX) → инициатива начинается с FEAT-YYY.

### N.0 Операционный цикл
Делегированное исполнение по `guides/adr-execution.md` Часть B (оркестратор) + Часть C (бриф субагенту).

### N.1 Сквозные требования (для КАЖДОЙ фичи — часть AC, не полиш)
- Типизация: 0 подавлений типов, decode/validate на границах
- Безопасность: deny-by-default, per-method authz, негативные тесты
- ADR-специфика: … (перечислить, что относится к ЭТОЙ инициативе)

### N.2 Живой документ
Правила актуализации — `guides/adr-execution.md` Часть B. Обновлять §N.3 (статус) + §N.6 (журнал) после КАЖДОЙ фичи. Keystone-правки — прямо в §N.5.

### N.3 Фазы и фичи
Легенда статусов: `⬜` не начато · `🚧` в работе · `✅` выполнено · `⚠️` выполнено с отклонением.

**Фаза 1 — …**
| ст | FEAT | имя | Зависит | Что даёт |
|----|------|-----|---------|----------|
| ⬜ | NNN | <имя> | — / FEAT-XXX | <суть> |

### N.4 Критический путь
    Фаза 1:  NNN ──► NNN+1 ──► NNN+2
    Фаза 2:  NNN+3 ──► NNN+4

### N.5 Keystone-контракты (specs-first)
Контракты, общие для ≥3 фич. Типы фиксируются ДО кода, рассогласование падает на компиляции.

### N.6 Журнал реализации
| дата | FEAT | impl.md | заметки |
|------|------|---------|---------|

### N.7 Проверка полноты + Out-of-scope
Что из §2 ADR покрыто фичами (соответствие FEAT ↔ цель). Что явно вне scope.
```

## Часть B — Работа оркестратора (B.1 запуск цикла · B.2 приёмка фичи · B.3 стоп-декомпозиция · B.4 живой документ · B.5 дельта-возврат)

### B.1 — Запуск цикла

```
1. Подготовить ADR (см. Часть A) → ЗАКОММИТИТЬ в develop ДО начала делегирования.
2. Для КАЖДОЙ новой фазы (не только первой) — Specs-First-гейт Части G: spec-субагент пишет
   spec.md ВСЕХ фич фазы + keystone; перечитка/валидация G.0. Без чистого прохода — код не начинать.
3. Выбрать следующую фичу(-и) из таблицы (⬜, все зависимости ✅). Независимый фронт → параллелить
   (несколько Agent-tool в ОДНОМ сообщении), не цедить по одной.
4. Сформировать бриф субагенту (Часть C).
5. Делегировать субагенту через Agent tool (или эквивалент IDE).
6. Принять сжатую сводку → merge под lock (Часть H.1) → проверить живой документ обновлён →
   после БАТЧА мержей — полный интеграционный гейт (H.6) → следующая фича.
```

**Важно:** не коммить ADR после старта фич — это сбивает нумерацию и keystone-ссылки. ADR закоммичен ДО делегирования.

### B.2 — Приёмка фичи (что проверяет оркестратор)

После сводки субагента оркестратор делает **минимальную** проверку, не открывая код:

```
□ Статус фичи в таблице ADR обновлён (⬜→✅ или ⚠️)
□ Строка в журнале ADR добавлена (дата · FEAT · ссылка impl.md · заметки для будущих фич)
□ Если менялся keystone-контракт — правка применена ПРЯМО в §N.5 ADR
□ Тесты зелёные (по сводке субагента)
□ Если были отклонения от spec — зафиксированы в impl.md и журнале
□ Ревью пройдено по КАЖДОМУ коммиту фичи (ADR-010): для каждого коммита git log <base>..<branch>
  есть <short-hash>-review.md с вердиктом PASS/WARN и закрытыми blocker (сверка §9 гайда
  commit-review.md — git log ↔ review-файлы; реестр — лишь витрина, гейт по файлам)
```

Если хотя бы один пункт не выполнен — **вернуть субагента на доработку**, не переходить к следующей фиче. Это частая причина stale-картины для следующего субагента.

> **Врезка: Очистка worktree (гигиена оркестратора).** Смерженные worktree копятся десятками за волну и мешают ориентироваться, какие ветки ещё живы. Поэтому после **каждого** подтверждённого merge фичи (не пачкой в конце волны) оркестратор запускает `scripts/cleanup-worktrees.sh` (сначала `--dry-run`, чтобы увидеть план). Скрипт — тонкий врэппер над `scripts/sync.sh --cleanup` (единая логика уборки); сам себя защищает: удаляет только влитое в базовую ветку (`git merge-base --is-ancestor`), пропускает залоченные, **грязные** и «свежие» (`< FRESH_HOURS`) worktree с явной причиной пропуска. **Субагент свой worktree не убирает** — это зона оркестратора (см. `feature-workflow.md` Шаг 12).

> **Честный статус: `✅` — только ПОСЛЕ merge + зелёных гейтов.** Сводка субагента «сделал, тесты зелёные» ≠ фича закрыта. Фича становится `✅` в таблице только когда её ветка **влита в интеграционную ветку** (по merge-протоколу Часть H) и **полный интеграционный гейт зелёный**. До этого — `🚧`. Не отмечай `✅` по одной сводке: композиция параллельных фич ловит классы, невидимые per-фиче (см. H.6 — полный гейт после батча).

> **Merge — не прямой командой.** Оркестратор мержит ветки субагентов только по **merge-протоколу Части H** (merge-lock · ancestry/origin-parity · `--no-ff` · post-merge checklist). Особенно при параллельных фичах: два merge в одну ветку одновременно бьются. После **батча** мержей — полный интеграционный гейт (H.6).

### B.3 — Когда ОСТАНОВИТЬСЯ (не «новая фича мид-стримом»)

Если в ходе реализации появилась **новая фича**, не запланированная в таблице — это сигнал **СТОП + пере-декомпозиция** (новой фичи мид-стримом не появляется). Исключение — заранее объявленный **прикладной трек, который растёт штатно** (например, набор skill'ов или сущностей). Такой трек — расширение по плану, не сюрприз.

### B.4 — Живой документ: анти-конфликтная форма (при параллельных фичах)

Когда несколько субагентов работают параллельно, живой документ ADR становится точкой гонки. Форма, устраняющая конфликты:

```
□ Журнал — строго APPEND-в-КОНЕЦ. Новая строка добавляется только в хвост;
  никто не вставляет в середину и не переписывает чужие строки.
□ Статус-таблица — каждый субагент касается ТОЛЬКО СВОЕЙ строки (свой FEAT-NNN).
  Чужие строки не редактирует, даже «заодно».
□ Конфликт при мерже живого документа → стратегия «keep both»
  (сохранить обе версии строк), финально разруливает ОРКЕСТРАТОР — он видит картину.
□ Keystone-секция — точка гонки при параллельной работе: субагенты её НЕ правят напрямую,
  а возвращают keystone-дельту ТЕКСТОМ; вносит серийно ОРКЕСТРАТОР (см. Часть G.1).
□ Лимит записи журнала: ~10 строк ДИСТИЛЛЯТА на фичу (контракты, имена сущностей/
  портов/topics/таблиц, подводные камни), НЕ протокол работы. Протокол — в impl.md.
□ При разрастании: закрытые волны/фазы выносить в отдельный архивный файл
  (например adr/NNN-journal-archive.md), оставляя в ADR только АКТИВНУЮ фазу.
```

### B.5 — Дельта-правило возврата субагента

Субагент возвращает оркестратору **только дельту состояния**: что изменилось, вердикт (✅/⚠️/❌), разблокированные фичи, блокеры — **НЕ пересказ протокола** реализации. Целевой объём сводки — **~150 токенов**. Всё длинное («как именно делал», полный список файлов) живёт в `impl.md` и журнале, откуда следующий субагент прочитает при необходимости. Это держит контекст оркестратора узким на длинной инициативе.

> **Почему бриф настолько явный про «живой документ».** Это самый частый пропуск делегированного исполнения: субагент реализует фичу и забывает обновить таблицу/журнал → следующий субагент стартует на **stale**-картине (не видит, что фича готова; читает устаревший контракт). Поэтому Шаг 4 — **часть DoD**, а оркестратор его в B.2 **проверяет**.

> **Узкое doc-only-исключение изоляции через worktree.** Субагент, создающий **ТОЛЬКО новые doc-файлы** (спеки/ADR/гайды с нулевым пересечением по путям), может по **ЯВНОМУ решению владельца** работать в основном чекауте без отдельного worktree. Инварианты: (1) **нулевая коллизия путей** — только НОВЫЕ файлы, ничего существующего (кода/доков) не трогает; (2) **git-команды запрещены** (commit/merge/push/worktree делает владелец/оркестратор). Любое касание кода или существующего файла → немедленно обратно в отдельный worktree.

## Часть G — Specs-first гейт границы фазы + keystone-контракты ⚠️

Перед кодом **новой фазы** — отдельный проход **spec-субагента** (не имплементационного: он держит **всю фазу** в контексте, имплементационный — нет). Это гейт: пока он не пройден — код фазы **не начинается**.

```
1. ОДИН spec-субагент на фазу пишет spec.md ВСЕХ фич фазы (а не по одной перед реализацией)
   + заполняет keystone-секцию ADR: field-list-с-типами контрактов, от которых зависят ≥3 фичи.
   Это specs-first ДЛЯ КОНТРАКТОВ: тип фиксируется до кода → рассогласование падает на компиляции.
   Почему всё сразу — feature-workflow.md Шаг 2 «Specs First» (свежий контекст всей картины,
   раннее обнаружение конфликтов контрактов, корректные границы фич).
2. Keystone-типы ЗАМОРАЖИВАЮТСЯ в keystone-секции ADR (в своём ADR это может быть §N.5/§6.5 — см.
   скелет Части A). После заморозки они — единый источник; отдельная фича их молча не переопределяет.
3. Валидация спеков (G.0 ниже) — ОБЯЗАТЕЛЬНО, гейт НЕ пройден без неё.
```

**G.0 — перечитка и валидация спеков.** После того как spec.md всех фич фазы написаны и keystone заполнена — спеки **полностью перечитать** (не «по диагонали»). Можно (для фазы из многих спеков — желательно) запустить агентов: один читает все спеки разом (ловит **кросс-спек** конфликты), либо агент-на-спек, либо **адверсариальный** агент, которому поручено **ОПРОВЕРГНУТЬ** согласованность. Их вывод — данные оркестратору; правки в спеки/keystone — **ДО** кода. Проверить по каждому спеку **и по фазе в целом**:

```
□ Логика — нет противоречий (дизайн ≠ AC); шаги не ссылаются на несуществующее; нет циклов зависимостей
□ Связи — общий тип/контракт/порт/topic/таблица назван ОДИНАКОВО во всех спеках, что его делят;
   keystone-секция ↔ спеки согласованы; нет дубля контракта в shared-типах
□ Архитектура — соблюдены инварианты ADR и architecture.md: контракт до логики; границы фич
   («одна фича — одна ответственность», система рабочая после каждой); deny-by-default
□ Типизация — единый источник типов (рассогласование падает на компиляции)  # ADAPT: см. stack-specifics.md
□ Безопасность — каждый новый метод несёт явную authz; least privilege; фильтрация по владельцу;
   нет секретов в plaintext/логах; обязательные НЕГАТИВНЫЕ security-кейсы в AC
□ Сквозные требования §N.1 ADR — учтены в AC каждой фичи (это часть AC, не полиш)
```

Найдены проблемы — **исправить спеки и keystone ДО кода** (дешевле, чем переделывать реализацию). Только после чистого прохода — реализация первой фичи фазы.

### G.1 — Keystone-дельты вносит ТОЛЬКО оркестратор, серийно ⚠️

Keystone-секция — общий ресурс: при параллельной работе это точка гонки.
- Агент **не редактирует keystone-секцию ADR напрямую** в параллельной фазе — он возвращает **keystone-дельту ТЕКСТОМ** в сводке (какой тип/поле добавить/изменить и **почему**).
- **Оркестратор вносит дельты в ADR серийно** (по одной, видя всю картину). **Никогда не давай нескольким агентам редактировать ADR параллельно** — иначе merge-конфликт keystone-секции и риск потерять правку.
- В строго **последовательном** исполнении (один активный исполнитель) он может править свою keystone-строку прямо — гонки нет.

### G.2 — File-ownership fence при нескольких агентах на одном checkout ⚠️

Если несколько spec-агентов работают параллельно в **ОДНОМ** чекауте (независимые ветки фаз) — **fence обязателен** в брифе КАЖДОГО:

> «Создаёшь РОВНО файлы [точный список]. НИКОГДА не удаляй и не трогай другие файлы. Чужие untracked-файлы (`??` в `git status`) — **ИГНОРИРУЙ**, НЕ считай мусором.»

Без fence агент одной ветки может принять свежие спеки соседей за мусор и **удалить** их (реальный инцидент: соседи прошли дальше, не переэмитили — восстанавливали вручную по keystone-дельтам из отчётов). Альтернативы: worktree-изоляция каждого агента, либо сериализовать spec-агентов по фазам. Дефолт при параллели — **явный path-fence** (дёшев, срабатывает).

> **Size-протокол.** XL-фичи (несколько слоёв сразу / явно > File-Size-Policy) **пре-сплитятся ДО** реализации на под-номера (`NNN.a`/`NNN.b`); внутри сплита — **enabling-компонент раньше** (тот, на котором висят остальные). DoD под-фичи проверяет, что негатив-тест **не вакуумный** (падает при снятии гейта).

## Часть H — Merge-дисциплина и параллельные оркестраторы (выученные уроки) ⚠️

> Когда несколько субагентов/треков идут **параллельно**, а оркестратор проводит **ранние merge** в общую интеграционную ветку, возникает класс ошибок, которого нет в одиночном исполнении. Правила ниже дистиллированы из реальных инцидентов боевой инициативы — **обязательны при параллельном исполнении**. Стек-специфика помечена `# ADAPT:` (детали — `stack-specifics.md`).

### H.1 — Merge в интеграционную ветку — ТОЛЬКО через оркестратора, под merge-lock ⚠️

> ⚠️ **Модель доставки проекта.** Оркестратор интегрирует фичи **ЛОКАЛЬНО** — в интеграционную ветку инициативы (`feat/<initiative-slug>`, созданную `./scripts/task.sh new <slug>`), НЕ напрямую в `develop`. `develop` — интеграционная ветка **клиента**; доставка туда (`git push` + MR, merge) — **только пользователь** (§7 architecture.md, §8 гигиена). Ниже «интеграционный базис» = локальная ветка инициативы; финальный push/MR из неё делает пользователь. Базовый sync — `git merge origin/develop`.

Субагент/трек merge в интеграционную ветку **не делает** — он коммитит в свою ветку (через `scripts/commit.sh`) и сигналит «ready». Merge проводит **оркестратор** по протоколу:

```
1. Взять merge-lock (atomic `mkdir` lock-каталога) — защита от ПАРАЛЛЕЛЬНОГО merge: двое не пишут
   интеграционную ветку одновременно. Лок берётся ТОЛЬКО из ОСНОВНОГО чекаута: в worktree `.git` — файл-указатель,
   mkdir внутри него невозможен → fail-closed (это и нужно, а не обход).
2. ancestry-check: `git merge-base --is-ancestor <base> <branch>` — ветка ответвлена от актуального базиса.
3. origin-parity: локальная база == origin-базе (иначе след треков путается, идут idx-коллизии).
4. `git merge --no-ff <branch>` — merge-commit сохраняет «фича = отдельная ветка» (трассировка).
5. verify (post-merge checklist H.3) → снять lock (`rmdir`). **`git push origin` НЕ делает оркестратор** — доставка на клиента (push + MR) = пользователь.
6. Уборка worktree+ветки (B.2 врезка) — СРАЗУ после подтверждённого merge, не пачкой в конце волны.
```

### H.2 — «ready» валиден только при ЗАКОММИЧЕННОЙ ветке; переинвентаризация перед merge ⚠️

«Merge — не моя зона» ≠ «коммитить не надо». Субагент/трек ОБЯЗАН закоммитить в свою ветку атомарно по фичам (`git add` конкретными путями); гейты гоняются на **закоммиченном** состоянии (`git status` чист). Перед КАЖДЫМ merge оркестратор **переинвентаризирует ФАКТ дерева** (`git log <base>..<branch>` не пуст **и** `git status` чист в worktree), а не верит отчёту — **факт дерева важнее сводки**.

**Плюс — покрытие ревью (ADR-010).** Та же переинвентаризация проверяет, что **каждый** коммит `git log <base>..<branch>` имеет `ai/devlog/commits/<repo>/<short-hash>-review.md` с вердиктом PASS/WARN и закрытыми blocker (сверка git log ↔ review-файлы, `commit-review.md` §9). Есть непроверенный коммит (нет review-файла ИЛИ FAIL с незакрытым blocker) → **merge не проводится**, вернуть на доработку.

### H.3 — Post-merge checklist (после КАЖДОГО merge базиса в ветку) ⚠️

```
[ ] git merge origin/develop --no-edit                # подтянуть актуальный базис
[ ] переустановка зависимостей после merge                          # ADAPT: deps install (frozen-lock) — stack-specifics.md
[ ] codegen / симлинки workspace-пакетов, если стек требует         # ADAPT: proto-gen / workspace-linking
[ ] typecheck — БЕЗ веры в кеш билд-системы (cache-miss = честно)   # ADAPT: команды typecheck — stack-specifics.md
[ ] lint / format-check                                             # ADAPT
[ ] тесты (для параллельных merge — и пакетные/интеграционные, не только unit)  # ADAPT
[ ] grep conflict-markers ВКЛЮЧАЯ comment-регионы:
       grep -rE '^<<<<<<< |^>>>>>>> ' --include='*.*' . | grep -v node_modules | grep -v '/.git/'
    (маркер в КОММЕНТАРИИ не крашит парсер → молча маскирует реальные ошибки; гейт «проходит», долг копится)
```

> **Кеш билд-системы (turbo/nx/bazel/…) МАСКИРУЕТ латентные провалы** typecheck/lint — replay стейл-зелёных логов, чей cache-key не инвалидировался. На «финальном»/волновом прогоне форсируй пересборку (`--force`/аналог; `0 cached` в выводе = честно). Рутинные прогоны мид-фичи — кеш ок; сомнение → форс. # ADAPT: флаг форса под свою билд-систему.

### H.4 — Разрешение конфликтов: keep-both + ручное восстановление «разрезанных» объектов ⚠️

```
❌ Взять один блок, удалить «дубликаты» из другой стороны → unused-imports / потерянные кейсы диспетчера.
✅ Конфликт-регион может РАЗРЕЗАТЬ несвязанные объекты. Сохраняй ВСЕ imports из ОБЕИХ сторон +
   imports из базиса МЕЖДУ конфликт-регионами. Если одна сторона отрефакторила структуру (thin wrapper) —
   бери её WHOLESALE и ИНТЕГРИРУЙ фичи другой стороны внутрь; затем СВЕРЬ диспетчеры/switch на полноту
   кейсов ОБЕИХ сторон (typecheck/lint это НЕ ловят — ловят только тесты обеих фич). Прогони гейты после.
```

Живой документ (журнал/таблица) конфликтует **ОЖИДАЕМО** и разрешается **keep-both** (B.4): журнал — обе строки (порядок не семантичен, у каждой своя дата·FEAT); таблица — обе статус-правки. Финально разруливает **оркестратор**.

### H.5 — `git stash` ЗАПРЕЩЁН субагентам в worktree ⚠️

Stash-стек живёт в **ОБЩЕМ** `.git` на все worktree'ы: `pop` вытащит **ЧУЖОЙ** stash параллельного агента в твоё дерево (реальный риск потери десятков файлов чужого WIP). Субагенту stash не нужен — его worktree изолирован по определению. Временное состояние — только **commit в свою ветку** (амендится/сквошится) или отдельный файл в scratchpad. Обнаружил неожиданный stash — **доложи оркестратору**, не снимай со стека.

### H.6 — Полный интеграционный гейт после КАЖДОГО батча мержей ⚠️

Per-фичный ready-check зелёный **≠** композиция проверена. Классы, которые per-фича НЕ ловит (проявляются только вместе): пропущенная миграция, стейл-ассерты счётчиков соседних фич, щель между двумя правками общего инварианта, хрупкость чекеров на новый ввод. **После каждого БАТЧА мержей** (не после каждой фичи) оркестратор гоняет **полный гейт интеграционной ветки** (typecheck · lint/format · все тест-уровни · миграция-parity/snapshot, если есть) — обычно отдельным **дешёвым** агентом. # ADAPT: команды — stack-specifics.md. Красное → фикс-фича (`.a`-суффикс) **НЕМЕДЛЕННО**, до следующего батча.

### H.7 — Параллельно-branch коллизия разделяемого ресурса: перегенерация, не ручной ренейм ⚠️

N параллельных фич от ОДНОГО базиса, каждая инкрементит общий счётчик / занимает следующий **авто-нумеруемый** слот (миграция, регистрация) / дописывает строку живого документа. При мерже git даёт `add/add` или content-конфликт; слепой keep-both всего файла **ДУБЛИРУЕТ**. Разрул:

```
• Авто-нумеруемые артефакты (миграции и т.п.): отставшая ветка → git merge базис →
  ПЕРЕИМЕНУЙ свой артефакт на следующий свободный номер → ПЕРЕГЕНЕРИРУЙ производное
  (накопительный snapshot/индекс) генератором стека — НЕ правь руками.   # ADAPT: migration-gen проекта
• Счётчик/реестр: keep-both ОБА блока регистрации; значение-ассерт = ФАКТИЧЕСКОЕ число
  (не «+1» вслепую) — прогони гейт, он назовёт истинный count.
• Живой документ: append-регион журнала — авто keep-both; таблицы/architecture — ПОСТРОЧНО вручную
  + grep|sort|uniq -d на дубли ПОСЛЕ каждого merge (ловит «правку одной строки двумя ветками»).
```

### H.8 — Новое «приземление»/интеграционная точка → прошей ВСЕ сквозные реестры ⚠️

Когда фича добавляет объект, участвующий в **сквозной гарантии** (новая сущность под общий оркестратор, новый тип под exhaustive-обработку, новый обработчик под общий диспетчер), недостаточно **зарегистрировать** его в одном месте. Фича **В ТОЙ ЖЕ фиче** ОБЯЗАНА прошить объект во **ВСЕ** сквозные реестры/оркестраторы, которых он касается, и прогнать **ПОЛНЫЙ** соответствующий сьют. Узкий coverage-гейт покажет «зарегистрировано», но пропустит «не подключено к runtime». Бриф такой фичи (Часть C, Шаг 6) это перечисляет. # ADAPT: перечисли свои сквозные реестры в `stack-specifics.md`.

### H.9 — Сериализация тяжёлых гейтов машинным lock'ом ⚠️

**Параллельность СУБАГЕНТОВ ⊥ параллельность ГЕЙТОВ.** N субагентов, одновременно вышедших на тяжёлые гейты (typecheck/lint/test/build) на **ОДНОЙ** машине, складывают пики RAM (× N) → machine OOM / kernel panic (**реальный инцидент**). Оборачивай тяжёлые root-гейты **машинным gate-lock'ом** (`scripts/gate.sh`, atomic `mkdir`-лок, общий для всех worktree/сессий): семантика — **ОЧЕРЕДЬ, не отказ** (первый работает, остальные **ЖДУТ**). Агенты продолжают параллелить всё, **КРОМЕ** тяжёлых гейтов. «queue-timeout» (ждал очередь дольше лимита) — **НЕ красный гейт**, а сигнал **REQUEUE** (повтори команду; код выхода REQUEUE — источник истины в `scripts/gate.sh`), не откат ветки. # ADAPT: бюджет RAM/таймаут — под свой стек.

## Часть F — Ротация оркестратора (context handoff)

Контекст оркестратора всё равно переполняется на длинной инициативе (к ~10-й фиче). Когда близко к пределу — **передай эстафету свежему оркестратору** через **handoff-файл из 4 полей** (не пересказ всей истории):

```
1. Состояние ветки/веток — что смержено в интеграционную ветку, какие worktree живы,
   на какой фиче таблицы остановились.
2. Уроки-дистиллят — 5-10 строк ключевых выводов (контракты, gotchas), НЕ протокол.
3. Следующий шаг — конкретная следующая фича/действие из таблицы.
4. Фальсифицированные гипотезы — что уже пробовали и что НЕ сработало,
   чтобы преемник не пере-пробовал опровергнутое.
```

Преемник читает handoff + живой документ ADR + `memory.md` и продолжает цикл с того же места. Handoff-файл — временный (можно держать в `devlog/` или рядом с ADR); после подхвата эстафеты он не нужен.

## Часть D — Финальная приёмка ADR-инициативы (адверсариальная) ⚠️

Когда **все фичи** таблицы `✅`/`⚠️` — инициатива **ещё не закрыта**. Финальная приёмка доказывает, что цели ADR достигнуты и система **реально работает** (а не «компилится»). Перепроверку **делегируй субагентам-скептикам** (оркестратор сводит результаты) — это дефолт для независимого фронта (несколько Agent-tool в **одном** сообщении):

```
1. Сверка целей ADR (агент-скептик №1) — по разделу «Цель»/«Проверка полноты»:
   каждая цель/инвариант покрыт фичами и закрыт? Нет «забытых» целей? В журнале нет повисших
   расхождений? keystone-секция отражает ФАКТИЧЕСКИЕ контракты?
2. Полный зелёный прогон (агент-скептик №2): все тест-уровни + typecheck + lint/format + build
   — 0 fail / 0 предупреждений на актуальной интеграционной ветке ПОСЛЕ всех мержей (не на ветке фичи).
   # ADAPT: команды полного прогона — stack-specifics.md.
   Известный флейк → сверься с `process-metrics/known-flakes.md` ПРЕЖДЕ чем диагностировать.
3. Живая система (агент-скептик №3) — `guides/live-acceptance.md` (часть DoD инициативы):
   стенд поднят → реальный сквозной сценарий пройден (curl / настоящий браузер / e2e-скрипт).
   Убедиться ГЛАЗАМИ/дампом, что приложение ОТКРЫВАЕТСЯ и целевые потоки работают.
4. Адверсариальные инварианты (агент-скептик №4) — попытаться СЛОМАТЬ сквозные гарантии:
   deny ≡ not-exist, per-method authz, негативы безопасности, сессия-истекла→login. Цель —
   ОПРОВЕРГНУТЬ, а не подтвердить; уцелевшее = доказано. Sidecar-вердикт (Часть C формат).
5. Дрейф спеков (агент-скептик №5, опц.) — реализация не ушла от spec/keystone молча?
```

**PASS-with-caveats** допустим **только** если КАЖДЫЙ caveat явно замаплен на **отложенную фичу** (номер в таблице/бэклоге) — «допустимое известное ограничение», а не «забыли». Caveat без маппинга на отложенную фичу = **не PASS**.

**Дефект на приёмке = незакрытая цель** (не «починю потом»):
```
□ Завести фикс-фичу (под-номер .a, полный FEAT-NNN по feature-workflow.md)
□ Покрыть НЕ-ВАКУУМНЫМ регресс-тестом нужного уровня: red ДО фикса → green после
  (класс дефекта обязан больше не возвращаться; «просто починил без теста» — НЕ DoD)
□ Разбор первопричины: можно ли закрыть класс СТРУКТУРНО (lint-правило / compile-инвариант /
  completeness-тест)? Есть прицельная не-вакуумная проверка — добавь; нет — кратко обоснуй отказ.
□ Обновить живой документ → ПОВТОРИТЬ приёмку. Инициатива закрывается только при ЧИСТОЙ приёмке.
```

**Закрытие ADR** (только когда вся приёмка чистая):
```
□ статус-хедер ADR: «Принят» → «✅ Реализован» (+ дата)
□ architecture.md §10 (таблица ADR) + гейт актуальности §0/§2/§3 (инициатива почти всегда меняет картину)
□ memory.md: запись о завершении инициативы (ключевые gotchas) — пишет ОРКЕСТРАТОР
□ ретро процесса — `guides/process-retro.md` (если модуль включён): что в ПРОЦЕССЕ стоило дорого →
  фолоуапы в бэклог
□ Доклад пользователю: что сделано, gotchas, что вне scope (из §N.7) + все caveats с их отложенными фичами
```

> **Stub-first / честный статус.** Крупный сквозной контракт можно заложить **рано со стабом** (интерфейс/тип/пустой обработчик), а **живую активацию** вынести отдельной фазой — но тогда: (1) стаб явно помечен как стаб, (2) фича с ним `⚠️`, не `✅`, (3) caveat зафиксирован в журнале ADR и замаплен на активационную фичу (см. PASS-with-caveats). Стаб, выданный за готовое `✅`, — тихий техдолг: следующая фича строится на несуществующем поведении.
