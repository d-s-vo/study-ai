# Охранная обвязка (security rails)

Защита от утечки артефактов агентской разработки (следов ИИ/агентов/системы `ai/`, номеров задач,
маркера `~wip~`, секретов) в клиентские git-репозитории (`github.com/d-s-vo/nuxt4-ts-project-cbook`). Внутренняя дока.
Весь код обвязки — POSIX/bash 3.2-совместимый (macOS-совместимость — инвариант, не менять на
bashisms без явной причины).

> Модуль M6 (режим секретности «0 следов»). Этот файл описывает полную конфигурацию M6=ON
> (клиентский код, ИИ-разработка не должна быть видна заказчику). При M6=OFF (внутренний проект,
> использование ИИ официально принято) большая часть механизмов ниже — стоп-словарь следов ИИ,
> блок FEAT-номеров, `~wip~`-детектор — снимается или ужимается до гигиены секретов/ПДн; секции
> «Секреты и ПДн» и «Клетка для агентов» остаются в любом случае (это не про секретность, а про
> безопасность выполнения агента). См. `docs/module-matrix.md` шаблона.

## Модель угроз и зоны

- **Клиентские репы** (`cbook`): НЕ должны получить НИКАКИХ следов ИИ/агентов/системы
  (при M6=ON); в любом случае — никаких секретов и данных вне явного назначения коммита.
- **Корневая репа `study-cbook-ai`** (сам workspace, `origin`): следы системы здесь допустимы,
  но НЕЛЬЗЯ секреты и код заказчика.

Если клиентские репозитории живут как bare-клоны, разделяемые несколькими worktree (основной +
task-worktree) — `core.hooksPath`, выставленный на bare, применяется ко всем worktree сразу
(выставляется идемпотентно `scripts/bootstrap.sh`).

## Что построено

### Словари (`githooks/`)
- `stopwords.txt` — стоп-словарь (regex по строке, `#` — комментарий, кейс-инсенситивный скан):
  переносимое ядро следов ИИ (имена моделей/вендоров, служебная терминология методологии, номера
  задач, `~wip~`, трейлеры авторства, внутренние хосты) + `{{...}}`-слоты под проект. Не должен
  содержать проектную конкретику как хардкод.
- `allowpatterns.txt` — допуски: строка, матчащая эти паттерны, исключается из срабатывания
  стоп-словаря (легитимный `User-Agent`, диффы существующих клиентских доков, плейсхолдеры).

### Общий сканер (`githooks/lib/scan.sh`)
Источится (source) хуками и обёртками. Функции: `scan_text_file`, `scan_stream`, `scan_string`,
`scan_is_allowed`. Печатает нарушения (паттерн + № строки + текст), возвращает 0 (чисто) / 1 (грязно).
Кириллица в словаре (если используется) дублируется в капитализированном виде на случай, если BSD
`grep -i` не фолдит Unicode.

### Хуки клиентских реп (`githooks/client/`, подключены через `core.hooksPath`)
- `pre-commit`:
  1. Блок НОВЫХ (`--diff-filter=A`) файлов с запретными именами (`CLAUDE.md`, `AGENT*.md`, `spec.md`,
     `impl.md`, `retro.md`, `*.jsonl` и т.п.). Правка СУЩЕСТВУЮЩИХ клиентских доков (CLAUDE.md)
     — разрешена.
  2. Блок любых staged-файлов в путях `.claude/`, `.ai*`, `ai/`; скан имён файлов по стоп-словарю.
  3. Скан ДОБАВЛЕННЫХ строк (`git diff --cached`, строки `+`) по стоп-словарю, включая маркер
     `~wip~` (`~[[:space:]]*wip[[:space:]]*~`).
  4. Секрет-детектор (приватные ключи, облачные ключи, `PASSWORD=`/`SECRET_KEY=`/`TOKEN=` с реальным
     значением). Чувствительные данные проекта — боевые креды БД/S3(MinIO)/API-токенов/Cloudflare Tunnel из `.env`: наружу не выносить и в тестах не использовать (тесты — на `.env.testing` с `test_*`-значениями). Специальных таблиц ПДн у кулинарного приложения нет, поэтому ПДн-детектор в клиентском pre-commit оставлен закомментированным — включить, если появятся домены с ПДн.
- `commit-msg`: стоп-словарь по сообщению + явный блок трейлеров авторства ИИ (`Co-Authored-By`,
  `Generated with` и аналоги).
- `pre-push` (жёсткий, три условия):
  1. имя ветки не под запретом (служебные префиксы `ai-`, `claude`, `wip`, имя `study-cbook-ai`…);
  2. существует `.push-allow` в корне workspace и содержит имя ветки (строкой);
  3. ни один исходящий коммит диапазона (`git rev-list`), ни сообщение, ни добавленные строки диффа
     не содержат стоп-слов; дополнительно сканируются автор/коммиттер (`%an/%ae/%cn/%ce`) —
     не должны выдавать служебную идентичность агента.

### Хук корневой репы (`githooks/root/pre-commit`, подключён в `study-cbook-ai/.git`)
Блокирует секреты по именам (`*.env`, `*secrets*`, `id_*`, `*.pem`, `*.key`) и по содержимому
(`BEGIN … PRIVATE KEY`, `PASSWORD=`, `SECRET_KEY=`, паттерны облачных ключей), а также код
клиентских репозиториев в staged (пути из `repos.conf`) — защита от `git add -f`.

Детектор содержимого сужен до «похоже на реальное значение»: после `=`/`:` требуется **≥8
непробельных символов** (отсекает односимвольные/короткие плейсхолдеры). Ложные срабатывания на
строки-примеры в гайдах гасит `githooks/allowpatterns-root.txt`: строки-примеры с `❌`/`✅`,
инлайн-код в backticks, плейсхолдеры (`<...>`, `{{...}}`, `«...»`, `replace-me`, `example`),
заголовки диффа зон `ai/` и `ai/ops/security-rails.md`.

### Обёртки (`scripts/`)
- `commit.sh [<worktree>] <message>` — человекочитаемый прогон ДО коммита: проверка `~wip~`, скан
  staged-диффа и сообщения, проверка формата сообщения `<type>: <описание> (conventional commits; type ∈ feat|fix|chore|refactor|docs|test|style|perf|build|ci)` (при M6=OFF —
  вырождается в тонкую обёртку над `git commit` без стоп-скана). Тесты/гейты НЕ гоняет (это зона
  процесса `ai/guides/`).
- `deliver.sh <repo> <branch> [--dry-run]` — ЕДИНСТВЕННЫЙ санкционированный путь пуша в клиентский
  репозиторий, **запускает только человек в интерактивном TTY** (реальный пуш: `[ -t 0 ]` +
  повторный ввод имени ветки для подтверждения; агенту запуск закрыт PreToolUse-хуком). `--dry-run`
  работает и без TTY (проверка):
  1. финальный скан всего исходящего диапазона (`<branch> --not --remotes=origin`);
  2. TTY-гейт + интерактивное подтверждение (репо/ветка/число коммитов, ре-ввод ветки);
  3. запись ветки в `.push-allow`;
  4. временная подстановка рабочего `pushurl` (из `remote.origin.url`);
  5. `git push -u origin <branch>`;
  6. гарантированный откат через `trap EXIT INT TERM`: `pushurl` → `DISABLED…`, ветка снята из
     `.push-allow`.

### Git-level запрет push
На bare-клонах и обычных клонах клиентских репозиториев `remote.origin.pushurl = DISABLED_use_deliver_sh`.
`fetch`/`pull` работают (используют `url`), прямой `git push` падает ещё до сети. `deliver.sh`
временно возвращает рабочий `pushurl`.

### Клетка для агентов (`.claude/settings.json`)
- `permissions.deny`: `git push`, `git remote set-url`, `git stash` (общий bare `.git` — stash
  одного агента виден всем; см. `../guides/coordination.md`).
  > **Область stash-политики (намеренная эшелонированность, не противоречие).** Три носителя
  > различаются по охвату по возрастанию строгости: `CLAUDE.md` формулирует правило «`git stash`
  > в worktree запрещён» (операционная дисциплина); `claude-pretool.sh` физически блокирует stash
  > при cwd в **клиентском** task-worktree (точечный энфорсмент горячей зоны); `settings.json`
  > `deny` — **глобально везде** (включая артефактную зону), как самый строгий верхний эшелон.
  > Глобальный deny сознательно шире doc-правила: общий `.git` делает любой stash небезопасным.
- `permissions.allow`: whitelist рабочих команд (git status/diff/log/add/fetch/pull, тесты, линтеры,
  локальные curl).
- `hooks.PreToolUse` (matcher Bash) → `githooks/claude-pretool.sh`: читает JSON со stdin, блокирует
  (`exit 2`):
  - `git push` (в т.ч. индиректный `git "$SUB" push`);
  - обход хуков `--no-verify` / `-n` у `commit`/`push` (детект `-n` — точный токен, без ложных на
    похожие короткие флаги);
  - переопределение `core.hooksPath` в любой форме;
  - индирекцию подкоманды через переменную, `eval` с git, подмену `GIT_DIR`/`GIT_WORK_TREE` вместе с git;
  - обращение к `github.com/d-s-vo/nuxt4-ts-project-cbook` в обход официальных каналов (curl/wget/произвольный git с URL);
  - инлайн-код на других интерпретаторах с git/сетью внутри (обход строкового разбора команды);
  - `git stash` при cwd внутри клиентского task-worktree;
  - правку `.push-allow`, `git remote set-url`, запуск `scripts/deliver.sh` (доставка — только
    человек в TTY);
  - `git commit` со стоп-словами в команде — **только в контексте клиентской репы** (по `.cwd` или
    явному `git -C <клиентский-путь>`); коммиты корневого `study-cbook-ai` стоп-скан не трогает,
    клиентские `commit-msg`-хуки — второй рубеж в любом случае.
- **Гейт `Write`/`Edit`/`MultiEdit`** (`githooks/guard-write.sh`): агент не может переписать сами
  хуки, `**/.git/config`, `**/.git/hooks/`, `.push-allow`, `scripts/lib/coord.sh`,
  `.claude/settings.json`, `.mcp.json`. Без этого гейтился бы только `Bash` — правкой файла
  обходилась бы вся обвязка.

### Санитизация координационных данных
- Санитизация полей брони (`githooks/coord-session-start.sh`, `_san`) перед вставкой в контекст
  сессии — booking-файл (расходится через общий `origin`) не может стать prompt-инъекцией в
  контекст другого агента.
- Валидация `--repo`/slug по `repos.conf` в `scripts/coord.sh`/`scripts/task.sh`.

`.push-allow` — в `.gitignore` корня workspace.

## Как отключить / обойти (для человека)
- Разовый коммит в обход клиентских хуков: `git commit --no-verify` (осознанно).
- Доставка: только `scripts/deliver.sh` (агенту push запрещён на трёх уровнях — permissions,
  PreToolUse-хук, `pushurl`).

## Остаточный риск — граница защиты (важно, инвариант 13)

Всё перечисленное — **эшелонированная защита, а не абсолютная граница**. Агент с доступом к
ssh-ключу и сети принципиально может обойти любой строковый разбор команды (сборка из фрагментов,
свой бинарь, экзотический транспорт); `guard-write` не спасёт при доступе к shell через непокрытый
канал. **Полная защита от скомпрометированного/инъецированного агента невозможна без изоляции на
уровне ОС.** В этом профиле модуль M5 (контейнерная изоляция) выключен — слоя sandbox/контейнер с
сетевым белым списком нет; `pretool`/`guard-write` остаются единственным и первым эшелоном. Это
осознанный архитектурный выбор: при честном агенте система держится многослойно, для защиты от
нечестного — нужна была бы контейнерная/OS-изоляция, которой в текущем профиле нет.

**Формулировка одной строкой:** хуки и permissions — эшелоны против ЧЕСТНЫХ ошибок и следов, не
граница против скомпрометированного агента с сетью и shell.

## Известные ограничения
- Хуки клиентских реп обходятся `--no-verify` **только человеком**: агенту это закрыто.
- Новый (не существующий) файл правил клиента блокируется как новый файл — добавление реально
  нового такого файла человеком требует `--no-verify`.
- `core.hooksPath` — локальная настройка git-репы; при переклонировании bare её нужно выставить
  заново (делает `scripts/bootstrap.sh` идемпотентно).
- Кейс-инсенситивность кириллицы (если используется) зависит от локали (`LANG=C.UTF-8` — работает).
