# PROJECT-BRIEF — контекст для агента, пишущего задачи (промпты)

Прочитай это ПЕРЕД тем, как формулировать любую задачу разработчику/исполнителю.
Цель брифа — чтобы план разработки был скорректирован под реальную ситуацию, а не под
ошибочную рамку «миграция Nuxt → Laravel 1:1».

---

## 1. Настоящая цель — ОБУЧЕНИЕ, а не продукт

Владелец учится **собирать и сопровождать enterprise-монолиты на Laravel** в стиле своих
референс-проектов **`listvafintess`** и **`av1`** (его существующие монолиты — эталон паттернов,
которые он хочет освоить). Их конкретные конвенции в этом workspace НЕ задокументированы —
**если нужны детали их структуры, спроси у владельца**, не выдумывай.

Учебный проект **Cookbook** — это **подопытный кролик** для отработки паттернов, а НЕ продукт,
который надо сохранить или точно перенести.

> **Следствие для планирования:** задачи должны быть **педагогичными** — инкрементальными,
> с пояснением «зачем» каждого enterprise-паттерна (Task / Repository / Resolver / DTO), с
> обозримыми диффами, которые владелец может отсмотреть и понять. Никаких «чёрных ящиков»
> и мега-задач на пол-проекта.

## 2. Это ПЕРЕПИСЫВАНИЕ, а не миграция

Стек Nuxt/Prisma **списан** — он больше не актуален. Мы **не портируем** Nuxt-код 1:1.

Сохраняем только:
- **общую идею** (кулинарная книга: список / просмотр / добавление с картинкой / удаление рецептов);
- **специфичные переиспользуемые блоки**, в первую очередь **BVI-панель** (доступность для
  слабовидящих: размер шрифта, темы, синтез речи — клиентская логика, переносится как
  Inertia/Vue-компонент, от бэкенда не зависит).

Всё остальное **строится заново** на целевом стеке. Известные дыры Nuxt-версии (нет auth, нет
серверной валидации, утечка ошибок наружу, небезопасная загрузка файлов) — это то, что нужно
**исправить/не воспроизводить**, а не переносить. Nuxt-код = **референс идеи и BVI**, не образец
для копирования.

## 3. Целевой стек и архитектура (источник истины — `ai/`, НЕ `CLAUDE.md`)

⚠️ Клиентский `CLAUDE.md` **удалён**. Правила проекта живут в workspace-каталоге `ai/`:
- `ai/architecture.md` (§0 роутер, §4 слои, §5 домен),
- `ai/guides/stack-specifics.md` (команды/тулчейн/инварианты),
- `ai/adr/002-*` (стек), `ai/adr/003-*` (слои), `ai/memory.md` (north star + статус).
Ссылайся в промптах на них.

Стек: **PHP 8.4 · Laravel 12 · MySQL 8 · Sail (Docker)**; Inertia + Vue 3 (`<script setup>`, TS strict)
+ Tailwind; **Spatie Laravel Data** (DTO) + `artisan typescript:transform`; **Filament 5**;
`whyme-agency/laravel-media` (медиа); качество — **Larastan (PHPStan level 10)** + **Pint** + **Pest**.

Строгий поток: `Request (FormRequest) → Controller → Task → Repository → DTO (Spatie) → Page Resolver → Inertia (Vue)`.
Незыблемо: `declare(strict_types=1)` в каждом `.php`; Eloquent/`DB` — только в `app/Data/Repositories/*`;
наружу (в Inertia/Vue) — **только DTO**, не сырые модели; вся серверная валидация — через Form Requests.

## 4. Реальное состояние репозитория (критично для плана)

- Клиентский репо (`nuxt4-ts-project-cbook`) сейчас содержит **только legacy Nuxt-код**.
  **Laravel-проекта НЕТ**: нет `composer.json`, `artisan`, `vendor/`, `phpstan.neon`, `.pint.json`.
- Каталог **`app/` занят Nuxt** (Vue-фронт: `app.vue`, `pages`, `components`, `composables`…).
  У Laravel `app/` — это бэкенд. **Коллизия.** Значит план обязан НАЧАТЬСЯ со скелета Laravel,
  который забирает `app/` под бэкенд, а фронт переезжает в `resources/js` (Inertia). Nuxt-фронт
  замещается; его переиспользуемые куски (BVI) переносятся.
- Поэтому первые задачи — это **greenfield-скелет**, а не «добавь каталоги в существующий Laravel».

## 5. Как скорректировать план разработки

1. Переформулировать рамку: **«переписывание с нуля, переиспользуя идею + BVI»**, а не миграция.
2. Последовательность:
   - **1a — Скелет Laravel 12 + Sail:** решить стратегию `app/` (замена Nuxt-фронта на Inertia в
     `resources/js`, удаление/архивация Nuxt-частей), поставить composer/автозагрузку/Sail/MySQL и
     пакеты (spatie/laravel-data, larastan, pint, pest, filament 5, whyme-agency/laravel-media).
   - **1b — Бэкенд-скелет:** каталоги слоёв + базовые классы (`BaseTask` с `handle`, `BaseRepository`),
     конфиги качества (**Larastan** L10, `.pint.json` c `declare_strict_types`), **enforcement слоёв**
     (изоляция Eloquent) через **Pest Architecture** или **deptrac** — обычный PHPStan level это НЕ
     делает; `.gitkeep` для пустых каталогов; **доказать, что правило краснеет** временным файлом-нарушителем.
   - **2+ — Доменные срезы снизу-вверх:** миграция → Eloquent-модель → Repository → DTO → Task →
     FormRequest → Controller → Resolver → Inertia-страница → Pest; сущности `Recipe`/`Ingredient`.
   - Перенести **BVI-панель** как Inertia/Vue-компонент.
   - **auth и серверную валидацию — сразу** (закрыть дыры Nuxt-версии), не откладывая.
3. Не предполагать наличие Pint/PHPStan до установки. Инструменты запускать **через Sail**
   (`sail bin pint`, `sail bin phpstan analyse`).

## 6. Ограничения процесса (чтобы промпты ложились в наш пайплайн)

- Любая правка клиентского репо идёт **циклом workspace**: `task.sh new <slug>` → работа в
  `tasks/<slug>` → `commit.sh` (скан чистоты + conventional) → пользователь `deliver.sh` →
  PR `feat → develop → main`. Промпт — это **спека задачи**; исполнитель сам оборачивает её в цикл.
  **НЕ включай в промпты шаги push/deploy** — они только человеку.
- **Режим «0 следов ИИ»** в клиентском коде/коммитах: не добавлять `CLAUDE.md`/`AGENT*.md`,
  не упоминать ИИ/агентов в коде и сообщениях коммитов.

## 7. Открытые решения — уточнить у владельца

- Стратегия `app/`: замещаем Nuxt целиком или сосуществование (вероятно — замещаем).
- Диск для `whyme-agency/laravel-media`: локальный или S3/MinIO.
- Какие конкретно паттерны/конвенции из `listvafintess` и `av1` воспроизводить (если владелец
  может поделиться их структурой — это лучший образец для «enterprise-стиля»).
